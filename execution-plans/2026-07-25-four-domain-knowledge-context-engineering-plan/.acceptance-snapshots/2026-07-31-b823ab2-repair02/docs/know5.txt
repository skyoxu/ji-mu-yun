# Ji Mu Yun 四域知识与上下文工程实施方案 v4

## 一、四个正交维度

全文统一使用“四个正交维度”。

### 1. Domain Scope

回答：当前任务属于哪个知识域？

```text
toolchain
phase
workspace
marketplace
```

### 2. Per-Domain Visibility

回答：某项内容在指定 Domain 中以什么方式出现？

```text
active
dependency
conditional
historical
excluded
```

Visibility 不是独立于 Domain 的全局属性，而是：

```text
visibility[domain]
```

同一个文件可以在 Toolchain 中为 `active`，在 Phase 中为 `excluded`。

### 3. Lifecycle Instance

回答：数据属于哪个实例？

```text
repository-source
repository-template
project-instance
run-artifact-view
```

### 4. Enforcement Level

回答：当前隔离强度如何？

```text
E0 unscoped
E1 retrieval-scoped
E2 context-bound
E3 filesystem-enforced
```

任何配置、Manifest、查询结果和运行证据都必须显式携带这四个维度，不能再使用一个 `scope` 字段混合表达。

## 四、Hosted LLM/Codex 必须使用三份入口清单

不能再用“九个调用点”代表全部 Hosted LLM/Codex。

当前架构明确规定三类共享入口：

1. `.NET` executable Codex：`CodexHostedProcessCommandFactory`；
2. `.NET` structured/read-only：`ILlmRouteEngine` / `LlmRouteEngine`；
3. Python：`scripts/sc/_llm_backend.py::run_llm_exec` 或薄包装。

正式实施必须生成三份独立、可重建的 inventory：

```text
codex-hosted-callers.v1.json
llm-route-engine-callers.v1.json
python-llm-backend-callers.v1.json
```

另生成一份违规清单：

```text
direct-llm-invocation-violations.v1.json
```

用于检测：

-直接构造 `codex exec`；
-直接调用 provider SDK；
-绕过 `LlmRouteEngine`；
-绕过 `run_llm_exec`；
-未经登记的 subprocess/model 调用。

每条 inventory 记录：

```json
{
  "caller_path": "...",
  "caller_symbol": "...",
  "entrypoint_family": "codex-hosted|llm-route-engine|python-backend",
  "route_id": "...",
  "operation": "...",
  "read_write_mode": "read-only|workspace-write",
  "account_binding": "...",
  "project_binding": "...",
  "current_context_mode": "legacy|observe|enforced",
  "required_tests": [],
  "migration_status": "unassessed|observed|migrated|blocked"
}
```

K13 的“无 bypass”不依赖一个人工填写的调用数量，而要求：

```text
三份 inventory 全部 migration_status=migrated
direct invocation violations=0
静态 guard 能阻止新增 bypass
inventory 与源码 snapshot 一致
```

共享入口变更必须运行对应共享测试和 caller-specific tests。当前 standards 已明确要求：

* executable Codex：`CodexHostedProcessCommandFactoryTests`；
* read-only LLM：`LlmRouteEngineTests`；
* Python backend：`test_llm_backend.py`。

## 五、Hosted Context Manifest 必须组合现有合同

新 Manifest 不是新的 route recovery 或 prompt-security 权威。

它只负责把现有合同结果聚合到一次 run-bound context dispatch 中。

现有 Phase 标准已经要求：

* `hosted-route-recovery-order.v1`；
* `hosted-route-forbidden-source-scan.v1`；
* exact in-memory execution prompt scan；
* `execution_prompt_hash`；
* `persisted_prompt_hash`；
  -数据库 `project_route_prompt_evidence_bindings`；
* same-project succeeded run binding；
* source hash 重新计算；
  -最新 live acceptance blocker 优先。

因此 Manifest 采用引用组合，而不是复制这些语义：

```json
{
  "hosted_route_contracts": {
    "recovery_order": {
      "contract_id": "hosted-route-recovery-order.v1",
      "evidence_ref": "...",
      "evidence_sha256": "..."
    },
    "forbidden_source_scan": {
      "contract_id": "hosted-route-forbidden-source-scan.v1",
      "evidence_ref": "...",
      "execution_prompt_hash": "...",
      "persisted_prompt_hash": "...",
      "status": "clean"
    },
    "database_binding": {
      "binding_id": "...",
      "run_id": "...",
      "project_id": "..."
    },
    "live_acceptance": {
      "blocker_ref": "...",
      "blocker_sha256": "...",
      "observed_at_utc": "..."
    }
  }
}
```

组合验证器必须调用或验证现有合同产物，不允许：

-重新定义八源恢复顺序；
-自行计算另一套“允许来源”；
-用 Manifest 内自声明 hash 替代 authoritative recomputation；
-用旧 route state 覆盖最新 live blocker；
-把 `source_boundary_not_applicable` 的缺失当成默认豁免。

Manifest 的职责仅是证明：

> 本次 run 实际使用的 Project snapshot、恢复合同、prompt scan、数据库绑定和 live blocker 是同一组、同一项目、同一时刻可接受的上下文。

## 六、Manifest 签名、防重放和密钥轮换

### 1. Manifest 使用三段结构

```json
{
  "signed_payload": {},
  "signature": {},
  "validation_state": {}
}
```

HMAC 只计算 canonical `signed_payload`。

明确排除：

```text
signature
validation_state
manifest_hmac 本身
```

### 2. signed_payload 必须包含

```json
{
  "manifest_id": "...",
  "run_id": "...",
  "attempt_id": "...",
  "dispatch_id": "...",
  "account_id": "...",
  "project_id": "...",
  "workspace_id": "...",
  "issued_at_utc": "...",
  "expires_at_utc": "...",
  "nonce": "...",
  "max_uses": 1,
  "policy_revision": "...",
  "profile_revision": "...",
  "repository_snapshot_id": "...",
  "template_snapshot_id": "...",
  "project_snapshot_id": "...",
  "allowed_write_paths": [],
  "output_targets": []
}
```

### 3. signature 必须包含

```json
{
  "algorithm": "HMAC-SHA-256",
  "key_id": "...",
  "signed_payload_sha256": "...",
  "hmac_base64": "..."
}
```

### 4. validation_state 由服务端运行时生成

```json
{
  "revocation_status": "active|revoked|expired|consumed|superseded",
  "nonce_status": "unused|consumed",
  "validated_at_utc": "...",
  "gate_result_id": "..."
}
```

### 5. 防重放规则

* `nonce` 在 `key_id` 范围内唯一；
* dispatch 前以数据库事务原子标记为 consumed；
* `max_uses` 默认为 1；
* retry 必须创建新的 `attempt_id`、`dispatch_id` 和 nonce；
  -已 consumed、expired、revoked 或 superseded 的 Manifest 必须拒绝；
* Manifest 不能跨 run、project 或 account 使用；
  -时钟偏差容忍值由服务端 policy 明确声明。

### 6. 密钥管理

-签名密钥来自 host secret store；
-不得写入项目、Manifest、日志或子进程环境；
-子进程只能得到 Manifest ID 或只读副本；
-当前签名 key 和可验证旧 key 使用不同状态；
-key rotation 不得让未过期的合法 Manifest 无法恢复，除非明确撤销；
-key ID、启用时间、停签时间和撤销状态由服务端管理。

新增签名、nonce 和撤销存储属于 DB/secret 合同变化，必须包含：

-数据库 migration；
-旧数据库升级；
-持久化重启测试；
-key rotation 测试；
-revocation 测试；
-恢复测试；
-并发 nonce consumption 测试。

## 七、不可信数据的业务能力和控制面限制

“不可信”不代表“忽略内容”。

正确规则是：

> 不可信内容可以决定已授权操作范围内的业务输出，但不能改变控制面权限。

例如项目 GDD 可以决定：

-做什么游戏；
-角色、地图和玩法；
-需要哪些 UI；
-模块业务需求；
-素材风格。

但不能决定：

* Agent 的系统角色；
  -Domain Scope；
  -工具列表；
  -允许读写路径；
  -网络权限；
  -secret；
  -sandbox 模式；
  -输出文件目标；
  -账号或项目身份；
  -是否绕过测试、scan 或 gate。

信任标签不能只根据文件名确定，必须由以下组合确定：

```text
source origin
+ Lifecycle Instance
+ canonical path
+ source snapshot
+ registry revision/hash
+ package publication status
```

示例：

-根仓 `AGENTS.md` 只有在 Repository Source lifecycle 中，并且与服务端登记的 policy revision 对应时，才可作为 `trusted_service_policy`。

* Seeder 复制到项目内的 `AGENTS.md` 默认是项目数据或模板数据，不自动继承根仓权威。
  -项目内修改的同名 `AGENTS.md` 不能提升为服务端规则。
  -审核后的 Marketplace Skill 只有精确 package hash 命中 Published Skill Registry 时，才能获得指令资格。
  -历史 ADR 和旧 overlay 即使文件名合法，也只能是 `untrusted_historical_content` 或历史参考。

## 八、确定性中文与代码检索 Tokenizer

定义版本化 tokenizer：

```text
jimuyun.hybrid-zh-code.v1
```

同一 tokenizer revision 下，查询和文档必须使用相同算法。

### 1. Unicode

-严格 UTF-8；
-Unicode NFC；
-拉丁字符使用 invariant lowercase；
-保留原始文本位置映射；
-不依赖操作系统 locale。

### 2. 中文

连续 Han 字符串生成：

-完整连续短语；
-单字符 token；
-重叠双字符 token；
-长度不超过配置上限的重叠三字符 token。

v1 不使用动态词典和在线词库，避免依赖升级改变排名。

### 3. 代码和标识符

以下边界均拆分：

```text
camelCase
PascalCase
snake_case
kebab-case
dot.path
slash/path
namespace::symbol
```

同时保留：

-完整原始标识符；
-规范化完整标识符；
-拆分后的各部分。

例如：

```text
CodexHostedProcessCommandFactory
```

产生：

```text
codexhostedprocesscommandfactory
codex
hosted
process
command
factory
```

### 4. 特殊标识

以下内容作为不可再分的高权重 token 保留：

* ADR ID；
  -route path；
  -error code；
  -contract ID；
  -Schema version；
  -CLI option；
  -environment variable；
  -SHA/hash；
  -project/run ID。

### 5. 版本确定性

以下内容进入 build manifest：

```text
tokenizer_id
tokenizer_revision
normalization_revision
ranking_revision
dependency_lock_hash
```

依赖升级导致 tokenizer 或 ranking 改变时，必须生成新的 build generation，不允许静默覆盖旧排名。

## 九、Evaluation 的集合和 Glob 语义

### 1. Required source groups

```json
{
  "required_source_groups": [
    {
      "group_id": "phase-auth-code",
      "patterns": ["PhaseA.Platform/Security/**"],
      "minimum_hits": 1,
      "required_top_k": 5
    }
  ]
}
```

含义：

-每个 group 都必须满足；
-group 内多个 pattern 是“任一匹配形成候选集合”；
-至少命中 `minimum_hits` 个不同来源；
-必须在指定 top-k 内。

### 2. Required all matches

只有明确要求某个 glob 的所有文件都出现时，使用：

```text
required_all_matches
```

普通 eval 不默认使用“glob 全部命中”。

### 3. Forbidden source

```text
forbidden_patterns
```

任何一个结果匹配任何 forbidden pattern，即算失败。

### 4. Precision 的相关性全集

不能根据运行结果临时推断。

每个 evaluation case 必须显式声明：

```text
relevant_source_groups
```

评估开始时，在固定 source snapshot 上展开所有 glob，并把展开后的相关集合写入 evaluation result。

因此：

```text
precision@k =
top-k 中属于冻结 relevant set 的结果数 / k
```

```text
recall@k =
top-k 中命中的冻结 relevant set 数 / relevant set 总数
```

Eval result 必须记录：

* snapshot ID；
  -pattern expansion；
  -relevant set；
  -ranking revision；
  -tokenizer revision；
  -top-k 完整顺序；
  -tie-break 依据。

K0 不得：


* K0 基线；
  -build 验证；
  -evaluation；

浏览器 readback 只能返回脱敏摘要和逻辑 ID。

## 十二、Context Assembler 资源预算

每个服务端 Route Policy 必须显式提供数字预算，禁止 `unlimited` 或隐式默认值：

```json
{
  "max_artifact_count": 64,
  "max_total_raw_bytes": 1500000,
  "max_single_artifact_raw_bytes": 256000,
  "max_estimated_tokens": 120000,
  "token_estimator_revision": "jimuyun-context-estimator.v1"
}
```

这些数值是初始 profile，必须在 K0/K6 评估后校准；生产变更通过 policy revision 完成。

### 1. 确定性选择顺序

#### Tier 0：不可遗漏的控制面内容

* trusted system/service/route instructions；
  -Scope Policy；
  -Manifest contract；
  -安全和输出约束。

超预算则 fail closed。

#### Tier 1：不可遗漏的当前运行事实

-现有 recovery-order 所要求的当前来源；
-最新 live acceptance blocker；
-当前 route state；
-当前 source-boundary evidence；
-必要 contract。

超预算则 fail closed。

#### Tier 2：项目核心业务输入

-当前 GDD；
-project identity；
-当前目标；
-明确请求的素材和模块。

可按 route policy 分段，但不能静默丢失。

#### Tier 3：检索候选源码和测试

按以下顺序：

```text
required source
→ exact ID/route/symbol match
→ retrieval score descending
→ graph distance ascending
→ canonical path ascending
```

#### Tier 4：历史、conditional 和补充参考

最先截断。

### 2. 截断要求

不得简单截断任意文件中间字节。

允许的 deterministic reduction：

-优先使用已验证的结构化 section；
-按 heading 或符号边界裁剪；
-保留 source path、section、hash 和裁剪范围；
-同一 snapshot、policy 和 query 必须产生相同结果。

### 3. 遗漏证据

Context assembly 必须输出：

