知识库不再是“需要维护的文档体系”，而是对现有仓库进行编译后生成的机器检索投影。

原始代码、ADR、architecture、workflow、execution-plan、日志等继续保留原位；知识库只负责分类、过滤、压缩、建立索引和生成检索词，不成为新的人工事实来源。

一、先确认你当前最重要的改造目标

第一阶段不是重新设计全部文档，而是：

让默认进入 Phase 服务上下文的 Agent，看不到与 Phase 无关的本地正式工作流内容；但这些内容仍完整保留，供工具链维护任务显式调用。

仓库实际上已经有这个边界，只是目前停留在文字说明，没有落实成检索层面的强制隔离。

根 AGENTS.md 已经规定：

workflow.md 是仓库本地正式交付工作流；
它不是 Phase 浏览器/API 默认路径；
普通 Phase 工作不应进入 Taskmaster、Chapter 3–7、overlay generator、Chapter 6 review recovery 等内部工具链。

Phase A Cloud Runner overlay 也明确规定：

Phase 产品包含 Chapter 2 bootstrap 和 prototype lane；
Chapter 3–7 正式交付编排不属于 Phase 产品范围；
Phase 可调用 prototype workflow、prototype TDD、prototype scene；
Task triplet、overlay baseline、Chapter 5–7 均被排除。

但 workflow.md 自己仍宣称是“本仓库的日常可执行工作流”，并将 Taskmaster、Chapter 3–7 和 review pipeline 作为默认路径。

所以问题不是缺少边界规则，而是：

Phase-first 边界没有被编译成 Agent 的默认检索范围。

二、四层知识库应改成“四个机器检索 Scope”

可以继续使用你的四层名称，但实现上不要把它们当目录依赖层，而应当作为四个上下文配置文件：

toolchain
phase
workspace
marketplace

每次 Agent 或 Skill 工作前，必须先选择且只能选择一个主 Scope。

必要时可以加载该 Scope 明确声明的依赖模块，但不得直接搜索整个仓库。

推荐默认关系
Scope	默认内容	可条件加载	默认屏蔽
toolchain	VDD、Quick Dev、Bootstrap Review、BMAD、workflow、仓库维护脚本	Phase 或 Godot 代码，用于维护工具链适配	用户运行数据、市场内容
phase	PhaseA.Platform、Caddy、Phase API、账号、GDD、运行、集群、Phase ADR	prototype、Godot kernel、指定工具链入口	workflow.md、Taskmaster、Chapter 3–7、BMAD 规划内容
workspace	项目 AGENTS、README、project.md、项目状态、素材、允许的 Skills、Godot 实现	Phase 提供的 API/route contract、共享 Godot 标准	根仓正式 workflow、平台内部实现、管理员规则
marketplace	package、Skill、素材、发布、评估、安全审核	Phase capability 和沙箱契约	内部工具链、平台密钥、用户项目私有状态
三、当前 architecture 和 ADR 的正确归属
1. workflow.md：工具链 Scope

workflow.md 的主体并不是 Phase 服务工作流，而是原本模板/游戏业务仓的正式交付流程。

它包含：

Task triplet 初始化；
PRD/GDD 到任务生成；
overlay 生成；
contracts baseline；
Chapter 5 semantic stabilization；
Chapter 6 正式任务交付；
Chapter 7 UI wiring。

例如 Chapter 3 明确围绕 .taskmaster/tasks/、需求覆盖矩阵和 task triplet 构建。

因此应标记为：

scope: toolchain
visibility:
  toolchain: active
  phase: excluded
  workspace: conditional
  marketplace: excluded

这里的 workspace: conditional 是为了保留未来某个独立游戏仓显式启用正式本地交付工作流的能力；Phase 创建的普通用户项目不默认加载。

2. docs/architecture/base/**：游戏工作区模板/共享 Godot Kernel

Base 目录本身声明：

它是 Base-Clean；
使用 ${DOMAIN_*}、${PRODUCT_*} 占位符；
不允许具体 PRD；
主要对齐 Godot runtime、安全、性能、契约等 ADR。

所以它并不是 Phase 服务的基础架构文档。

更准确的归属是：

scope: workspace
module: shared-godot-kernel
visibility:
  workspace: active
  phase: dependency
  toolchain: conditional

Phase 只有在修改托管 Godot 执行内核、游戏运行语义、Godot UI 或质量门禁时才加载它。

普通 Phase API、账号、数据库、Caddy 或管理后台任务不应读取 base/**。

3. docs/architecture/phase-service/**：Phase 技术知识主入口

这个目录已经明确说明其 Scope 是：

Phase A/B 平台服务；
浏览器消费的 prototype routes；
Phase C 演进约束。

它已经有合理的模块拆分：

system overview
auth/accounts
metadata DB
workspace/artifacts
prototype routes/recovery
LLM/Codex
Caddy/runtime
audit/evidence
roadmap

因此它应成为 Phase Scope 的 R2 主投影，而不是再复制一套 Phase 技术文档。

知识编译器只需要扫描这些文件并生成更小的模块索引。

4. docs/architecture/overlays/**：默认屏蔽，按引用条件加载

你的判断基本正确：当前 overlay 体系主要来自原本的 PRD 功能纵切工作流。

唯一明显的 Phase overlay 是：

docs/architecture/overlays/PHASE-A-CLOUD-RUNNER/

但该文件目前仍标记为：

Status: Draft
Updated: 2026-05-10

而新的 Phase Service Architecture Index 已在 2026-06-28 对 Phase 实现重新扫描，并明确将该 overlay 称为“original Phase A overlay”，即原始设计来源，而不是当前唯一入口。

因此建议：

docs/architecture/overlays/**:
  default_visibility: excluded

docs/architecture/overlays/PHASE-A-CLOUD-RUNNER/**:
  phase_visibility: historical_dependency

只有以下任务加载它：

追溯某个 Phase A 原始决策；
检查现状是否偏离原始设计；
修改被该 overlay 引用、但尚未被新 ADR 替代的约束。

不能让普通 Phase 任务同时读取 phase-service/** 和完整 overlay，否则会增加重复上下文和旧事实冲突。

5. ADR 保持原目录，通过逻辑投影隔离

你不需要移动 docs/adr/**。

现在已经有两套合理的逻辑索引：

ADR_INDEX_PHASE.md：Phase 0032–0040。
ADR_INDEX_GODOT.md：Godot 和游戏 Kernel 0015–0031。

知识编译器直接把它们当作不同 Scope 的种子：

Phase ADR projection
  <- ADR_INDEX_PHASE.md
  <- 递归解析这些 ADR 引用的共享 ADR

Workspace/Godot ADR projection
  <- ADR_INDEX_GODOT.md

Toolchain ADR projection
  <- Bootstrap Review、VDD、Repository Maintenance 等 ADR
  <- 通过 standards 和 execution plans 自动发现

Phase 有时确实依赖 Godot ADR，例如 Phase Cloud Runner 引用了 ADR-0015、0018、0019、0025、0031。

因此不要使用“按编号范围完全隔离”，而要使用：

主 Scope ADR + 引用闭包。

八、需要引入“可见性”而不是简单 include/exclude

每个源文件在不同 Scope 下应有以下状态之一：

active
dependency
conditional
historical
excluded

含义：

状态	行为
active	默认进入该 Scope 的 RAG corpus 和索引
dependency	被 active 模块引用时自动进入
conditional	只有特定任务类型触发
historical	只用于追溯和冲突解释

例如：

十一、rg 和 RAG 的消费流程

知识编译器应为每个 Scope 生成一个确定性的搜索清单：

knowledge/projections/phase/search-files.v1.json
knowledge/projections/phase/search-terms.v1.json
knowledge/projections/phase/modules.v1.json

Skill 不再执行：

rg "keyword" .

而是执行：

knowledge-query --scope phase --query "prototype repair acceptance"

内部流程：

1. 从 phase/modules.v1.json 选模块
2. 从模块读取候选路径和 search vocabulary
3. 对候选路径运行 rg
4. 命中 public symbol、route、contract 或 test
5. 必要时扩大到 dependency
6. 不命中时才进入 conditional
7. 永不自动进入 excluded

RAG 也应建立四个独立 corpus，而不是先把全仓 embedding 后依靠 prompt 过滤：

rag-toolchain
rag-phase
rag-workspace-template
rag-marketplace

这会比在查询阶段用自然语言告诉模型“忽略 workflow.md”可靠得多。

十二、单人 + AI Agent 可以删除哪些复杂度

由于没有多人并行开发，可以不做：

module owner；
reviewer ownership；
-团队权限映射；
-跨 PR 文档锁；
-模块认领；
-复杂 merge conflict 处理；
-多人审批链；
-GitHub Issue 与知识条目双向同步。

但仍应保留：

Scope 边界；
-单一事实来源；
-生成文件不可手改；
-append-only evidence；
-SHA 和语义指纹；
-恢复 checkpoint；
-高风险路径的明确授权；
-当前状态和历史状态分离。

这些不是为了团队协作，而是为了防止同一个 AI Agent 在不同会话中互相冲突。

最终建议

你的场景不需要“人工维护的知识库”，而需要：

一个根据仓库事实自动生成四套 Context Projection 的知识编译器。

最先实施的边界应当是：

默认 Scope = Phase

workflow.md、Taskmaster、Chapter 3-7、overlay generation、BMAD
仅属于 Toolchain Scope

Phase 只通过显式 dependency 使用 prototype、Godot kernel
和少数经过枚举的工具链入口

现有文件全部保留原位：

workflow.md 不删；
architecture/base 不迁；
architecture/overlays 不删；
ADR 不分目录；
docs/workflows 不物理拆分。

只在生成的 catalog 和四份投影里改变它们的可见性。

这样第一阶段的改造成本最小，同时能立刻解决现在最核心的问题：Phase Agent 被旧模板工作流、Taskmaster 和 Chapter 3–7 内容污染上下文。
