## 2. 当前 UI/视觉的无环顺序

业务运行顺序与目录开发顺序不同：S1-02 先选择/冻结声明性风格基线 → 创建当前待验证场景并绑定 run/input → 执行原始检查与 S1-01C 采集 → S1-01A 汇总实际检查结果 → S1-01B 消费 validation/视觉及实际 UI 事实 → S1-03 按动作放行。实际服务可复用同一受控 run/harness，具体顺序由 spec 固化，但 validation 不读取最终 closure 作为自己的成功前提。

首次 snapshot 声明视觉任务，不预填未来成功；visual_validation_refs 等结果后补且遵守现有 hash identity。视觉采集不要求 validation/closure 已 succeeded，只需要已绑定输入和可执行场景；原始检查失败也可保留真实采集供诊断，最终闭环仍阻断。UI 修复动作不要求 UI 已完美。

建议 step1 串行：S1-01A、S1-02、S1-01C、S1-01B、S1-03。相关数据合同可一起评审，但不形成一个超大实现目录。平台 React/模块化不增加新的业务包，不在 Hosted UI 验收包内整体重建。

## 3. step2 的串行建议

S2-06 → S2-03A → S2-03B → S2-04A → S2-04B → S2-05 → S2-01 → S2-02 → S2-04C。

先把实际执行/出网/能力边界完成，再向真实内测用户开放自由文件编辑与项目执行。静态索引和变更关联在明确身份/来源之后接入；它们不决定游戏 runtime 是否通过。Skill 工单和单节点通知分别可以后置，入口各等其验收后显示；通知失败不新增 Runner 成功前提。S2-01 与 S2-04C 均按两组内部里程碑规划，缓存暖机不成为所有项目验收门槛。浏览器主动内容隔离在S2-05/S2-04B验收；编码可分“项目CRUD/执行”和“浏览器安全消费”两组内部里程碑，不新增需求目录。隔离未完成时关闭对应主动入口，不以此将受控文件编辑全面改为只读。

## 4. 各阶段释放条件

| 阶段 | 可以宣称的范围 | 必须先成立 |
| --- | --- | --- |
| step1 | 当前 route 的规范生产、风格与动作闭环可用 | 真实 validation/UI/视觉接通现有消费者，负例有效，未满足动作不开放 |
| step2 | 单节点测试的受控项目 Agent 能直接编辑/执行 | 实际隔离、资源、出网、工具授权、受保护具体结果及正常删除/既有恢复边界可证实；用户主动内容入口另须浏览器会话/网络隔离实证 |
| step2 静态增量 | 当前项目可查静态引用与可证实内容差异 | 无 Git 一致来源、归属和失效有效，不宣称 runtime 分析 |
| step2 工单/通知 | 工单或单节点通知对应入口可用 | 各自持久化、最小UI/角色隔离；工单引用真实批准Skill，通知可见/已读/修订/有效期一致 |
| step3 | 新生产节点可接收用户；站内通知可跨节点服务 | 自动分配、唯一归属、密码/会话交接及真实多机组合通过；通知按受众增量/基线补收通过后才声明该入口可用 |

入口同机只测试，正式角色切割不依赖项目搬迁工程。第二台“物理服务器”和第二个“可分配生产节点”应按实际部署计数；无论如何，新生产节点接收用户前必须完成其必需合同。

若正式单节点账号产品在step3多机前上线，S3-02的Identity密码最小登录、已选Direct Mail密码恢复及FR16账号软删除最小政策须先交付；token过渡和step3草案不得成为正式账号能力延期理由。单节点子范围不依赖未启用的自动分配或多机交接，不新增第十八个目录；BMAD按真实部署裁剪依赖并明确交付。正式公网部署的 HTTPS 最后收口保留在上线前，不能先上线不安全会话后补。

## 5. 外部审核输入

每包给出实际 HEAD/差异、FR→实现→AC 的当前映射、定向结果、所需真实 Windows/Godot/多机证据、兼容影响和未解决项。已有失败历史不改写。审核结论与正式工作流的完成权威按本地仓库现有规则处理，本包不新造外部 reviewer 调度器。

不扩展测试只为凑数量。成功、超时/取消、过期、缺/坏/错证据、权限越界按各包实际风险验证；无需另立通用失败验证器。

## 6. 9项修正的开放条件

这些条件复用现有preflight、服务端授权、受保护产物与浏览器读取策略，不建立新的gate平台。具体实现机制和配置在所属包BMAD/spec中固化，参数未定不能当作已经通过。

| 范围 | 未满足时的处理 | 可继续的范围 |
| --- | --- | --- |
| 用户HTML/SVG/试玩/HTML产物浏览器隔离（RV-P0-01） | 未验证的主动内容响应/预览入口阻断，不把父iframe保护当所有入口保护 | 受控项目编辑、桌面Godot验证、安全文本/下载；不承诺控制用户下载后的设备运行 |
| validation/UI/视觉具体生产结果可信绑定（RV-P1-01） | 结果与受保护记录不一致则不能当前通过、不能支持最终完成声明；保留真实失败/历史 | 正常编辑、按自身前置条件执行修复和重验；不为此新建第二验收器 |
| 首次风格/检查/视觉/closure顺序（RV-P1-02） | 缺必要真实证据阻断最终closure；不以未来成功为生成/修复启动条件 | 前置选择/冻结、当前场景生成、原始检查和真实采集 |
| 独立出网许可及定向来源限制（RV-P1-03） | 每次访问失败闭合；有效source_ref或公网IP不自动放行 | 合法关键词发现的批准来源；只有服务器许可工作流内部MCP例外 |
| 原生Agent配置/默认工具/模型秘密（RV-P1-04） | 未证明实际启动与秘密边界时不开放对应Agent执行；不退回自由联网/宿主身份 | 受控夹具编码测试；已证明的入口按有效权限运行 |
| 分卷准入/全部写入点/宿主输出收集（RV-P1-05） | 未取得预算不受理；实际限制/有界收集未生效时不开放执行；清理未知不释放承诺 | 已满足预算与限制的任务保持原队列/执行行为，不跨节点改派 |
| 静态来源/内容差异关联（RV-P2-01） | 源字节或图版本不符就stale/unavailable；并发观察不填独占因果 | 历史静态结果标明真实来源，游戏runtime由自己的既有检查决定 |
| 局部前台模块化（RV-P2-02） | 受影响surface未达本包新增AC就不宣称该包交付；不能拿此要求全站同时重写 | 无关页面保留，React按稳定surface迁移，不增加新需求目录 |
| 中心归属与节点承诺协议（RV-P2-03） | pending/准备未知不激活，不跨机重投或假定事务成功；新节点接收用户前必须实证 | step3继续作为复审草案；参数固化前不直接进入实现/生产 |

以上是真实开放前的实施要求；本轮仅修正文档，没有运行这些验收。

## 7. 组件增量的交付边界（版本4决定沿用）

S2-03B在既有安全日志基础上补SLS与小范围Sentry：先统一受限字段、版本及既有request/run关联，再接采集、过滤与有限故障验证。不要求先建设数据分析服务器、全量APM、Session Replay或Godot运行时分析。远端采集故障可安全降级为有界本地运维记录，不能改变真实run状态、验收或权限判定；若采集失败暴露了资源/秘密硬边界失效，仍按原安全条件阻断。

React迁移时，Sentry适配随各surface实施：复用一次初始化、必要ErrorBoundary、release标识和平台source map的私密构建上传；监控事件不代替该surface的功能/权限/失败验证。SLS负责日志查询与运维告警，Sentry负责平台错误分组和定位，不把同一原始游戏日志无限复制到两处。

S3-02密码恢复须包括邮箱所有权确认、限时单次重置、发送失败/重放/错账号负例、凭据变更后的会话撤销及秘密保护。邮件失败不改密码、不发登录会话、不激活pending账号；恢复成功后仍回到账号密码登录。邮件目标由平台预配置，不允许项目或用户传任意发送endpoint/重置回跳地址。

数据库技术和本地项目存储保持当前方向；新增查询缓存按第8节范围选择，容量/并行上限仍由S2-03A/B实际测量与承诺决定。多节点分配、准备、核对、心跳、交接及通知补收用原生合同实现，Make/Zapier不是上线依赖。API调试工具仍未确认，不把Postman“已使用”写入要求。

## 8. 共享消费、多实例及通知的实施/开放条件（版本5）

S2-01先完成无Git快照来源/静态索引，再补一个实际共享知识/demo消费者与有界查询适配；两组FR/AC分别进入BMAD/VDD，不一次重建知识控制面。S2-05的批准资源复制可复用现有批准来源与S2-04A接口，不要求先建S2-01缓存/全索引，因此上述串行顺序仍无环。S2-02随后连接可证明的复制/消费来源，不补历史假因果。

一个节点服务可承载多个Runner工作流；若实际选择多个独立.NET实例，同节点承诺/锁/lease/fencing与S3-02同角色认证共享子范围在启用该拓扑前实证通过，不能因S3主体草案而延期。S2-03A-AC09验证CPU/内存/进程聚合承诺竞争，AC10验证真实多实例（选择时），AC11验证服务缓存/队列与任务争用预算。进程内缓存并非跨进程共享，KV也不是资源锁或密码撤销权威。

S2-04C分别交付工单C1和站内通知C2。C2用保护数据库、明确受众/有效期/已读、周期刷新及本地事务通知变更；不要求先配置实时组件。S3-03后续复审再固化跨机鉴权增量、cursor/epoch、基线水位、保留/延迟/UTC策略，用真实离线/重启/丢回执/旧批次/游标越界验证。任何新节点对外开放通知入口前须具备补收；通知冷启动/同步积压本身不阻断已符合资源与安全合同的注册/任务。

查询缓存授权/私有scope不能证明时停止相应查询；有限回源失败保持unavailable。通知同步不可用显示待刷新/延迟，已知到期不延长，且不改变用户权限或项目结果；不得假承诺离线即时撤回。SignalR/Redis Pub/Sub/backplane若未来选用仅优化在线刷新，不能替代数据库记录与离线补收。所有新通道按S2-04B只授予固定受信服务用途，不向项目开放代理。

S1-01B-AC09验证必要视口遮挡/裁切负例；即使信号能触发，也不能完成当前UI闭环。它与聚合资源负例都是已有要求的明确验收，不新增通用校验器或Godot运行分析。

## 9. 三处执行与账号边界修订的交付条件（版本6）

| 修订 | 所属包与实证 | 开放/依赖规则 |
| --- | --- | --- |
| 账号/凭据在执行边界复验 | S2-05 FR16 → AC13；S2-04A FR08 接入同一机制 | 本轮开放的真实文件/Agent/队列/工作流入口须接通受理、dispatch 与关键发布复验。复用现有认证和 token，先于对应 Agent 能力开放，不等待 S3-02，也不新增 S2-04A 对 S2-05 的构建依赖 |
| 普通运行记录入库与读回脱敏 | S2-03B FR16 → AC13 | 普通数据库运行字段、API/读回及外部采集分别实证；不能只证明 SLS/Sentry 过滤。先于相应执行/读回入口开放，复用现有 SecretRedactionPolicy 和受保护诊断边界 |
| 最小账号软删除政策 | S3-02 FR16 → AC13 | 与正式单节点账号密码/恢复子范围一起固化和交付；不等待自动分配/多机交接。复用账号停用/启用，补授权、保留/容量与恢复语义，不做物理清除或全套管理面 |

上述修订不改变十七包的构建依赖图、文件正常删除政策或已有排除范围。runner job envelope/DTO、correlation 字段的最小落点及幂等键具体 schema 继续由所属包 BMAD spec/architecture 按现有合同细化，不另加独立需求或平台。这里是实施开放条件，尚未运行对应验收。
