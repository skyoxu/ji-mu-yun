我目前评为：P0 × 2，P1 × 4，P2 × 1。

P0

P0-1 — VDD 的 requirements universe 写错，而且没有真正 exact-cover mapping。

requirements-and-acceptance.md 写的是：

VCEC-001 through VCEC-043

但当前 Canonical Spec 实际是：

requirements：VCEC-001 ~ VCEC-036
acceptance：VCEC-A01 ~ VCEC-A43

当前 VDD 把两个 ID 空间混在了一起，而且只用几行概括“coverage must include...”，没有逐条：

VCEC requirement → acceptance → implementation slice

映射。

这恰好违反本项目最核心的 sound-and-complete cover 要求。现在无法证明例如 VCEC-008、021、027、034 等没有被大范围 slice 静默吞掉。

必须修成真实的 36 条 requirement mapping，不能写范围总括。

P0-2 — 当前 VDD 没有可执行的 RED/GREEN 和 terminal full validation。

implementation-contract.v1.json 的 RED/GREEN 是自然语言描述，例如：

“Manifest/hash/set/role drift fails before semantic work.”

不是可执行 command。并且 acceptance 中还用了：

"VCEC-A01..VCEC-A12"
"VCEC-A13..VCEC-A42"

这种 range string，而不是真实 acceptance ID 数组。

更严重的是 command-registry.v1.json 当前真正登记的主要验证只有：

Skill-input 旧 tests；
knowledge-context 旧 tests；
git diff --check。

而 VDD production 自己明确要求每个 slice 有 RED/negative command、GREEN command，并且 self-hosted plan 最终必须有一次 current terminal full validation。

现在没有命令能最终证明：

bmad-spec → VDD source freeze → exact-cover → repair → authorization preflight

所以当前 plan 即使全部 slice 被标完成，也无法证明任务完成。

S0 是：

按 VDD 自己的规则，这种情况应该是：

existing behavior / legacy-regression prerequisite

而不是新的 RED→GREEN implementation slice。

S0 应改成类似：

S0: preserve and harden existing bmad-spec producer

并用现有 producer bytes + regression/mutation fixtures 证明 VCEC-036/A43，不要重新实现它。
