一、总体策略

不要继续直接修改 8-17 计划合同并在同一个计划里自我验收。

应新增一个独立的控制面修复计划，例如：

这样可以避免“修改控制面代码的计划，依靠正在被修改的 coordinator 自证完成”的循环信任问题。

二、目标架构

现有 run-coordinator 虽然声明“caller supplies evidence, never a route”，但实际上仍从 request 同目录加载调用者提供的 authority、action receipts 和 machine evidence，然后直接根据两个布尔字段决定路由。相关逻辑在 acceptance_cli.py#L991-L1047。

目标架构应改为：

Coordinator 不再信任：

request 目录里的任意 JSON；
JSON 中自称的 "owner"；
调用者自行生成的 completed action receipt；
deterministicSourceSufficient、semanticReviewRequired 等调用者布尔字段；
静态构造的 recovery pointer、零值 telemetry。

Coordinator 只信任：

Acceptance 持久化运行目录；
binding-derived run ID；
受控 command registry；
append-only action/event 记录；
exclusive-create 的 action result receipt；
candidate、contract、Knowledge、Skill-input 的精确绑定；
finalize_deterministic_run 对整条证据链的重放结果。

仓库其实已经具备大部分基础设施：

start_or_resume_target_run
create_stale_linked_successor
recover_stale_persisted_action
inspect_persisted_run / resume_persisted_run
finalize_deterministic_run

修复时应该把这些能力串起来，而不是继续扩充 request-local 的伪 authority 协议。

1.1 新建 acceptance-coordinator-request.v3

  "preparedRunInput": {
    "path": "...",

  },

    "runInputHash": "sha256:...",
    "contractHash": "sha256:...",
    "knowledgeContextHash": "sha256:...",
    "skillInputReceiptHash": "sha256:...",

明确禁止出现：

route

其中 preparedRunInput.path 只是 locator，不是 authority。其内容必须再通过 canonical parser、Skill-input contract、目标目录约束和精确 hash 验证。

1.2 重写 run_coordinator

建议执行顺序：

验证 targetPlan 必须位于 execution-plans/。
验证 prepared run input、implementation contract、Knowledge context、Skill-input receipt。
调用 start_or_resume_target_run。

从受控 route-projection action 的结果读取路由。
deterministic 路由调用 finalize_deterministic_run。
semantic 路由发布绑定当前 run 的 typed handoff，然后停止。
最后执行 package validation。
Coordinator result 只投影持久化状态，不另造第二套事实。
1.3 生产者真实性校验

不要再用：

{"owner": "run-refactor-implementation-acceptance"}

作为 authority。

command ID；

输出文件路径和 hash；
exit status；

只有同时满足以下条件才算可信：

action 出现在该 persisted run 的 canonical DAG；
command ID 出现在该 run 的 command registry；
receipt 与 action claim/attempt 对应；
result 文件由该 action 的完成事件引用；
5.所有绑定与当前 run manifest 完全一致；
receipt 未重复、未缺失、顺序合法；
输出文件 hash 可重放验证。

路径位于 run 目录只是必要条件，不是充分条件。

1.4 路由判定

route projection 应改成受控 action 输出，例如：

{
  "schemaVersion": "acceptance-route-projection.v2",
  "decision": "deterministic_only",
  "matchedRules": ["changed-set-closed", "required-checks-machine-verifiable"],
  "sourceReadSetHash": "sha256:...",
  "requiredReceiptIds": ["..."],
  "candidateBindingHash": "sha256:...",
  "runId": "...",
  "authorizes": []
}

规则：

任一语义风险命中：semantic_review_required；
deterministic 所需 receipt 缺失：blocked，不能降级为 deterministic；

调用者布尔值：直接拒绝；
semantic 优先级高于 deterministic；
coordinator 不能自行把“证据不足”解释成 deterministic。
1.5 v2 兼容策略

旧 acceptance-coordinator-request.v2 可以保留只读解析能力，用于查看历史证据，但不得再发布当前完成结论。

建议返回：

legacy_evidence_untrusted

不能偷偷 fallback 到旧路径，否则新信任模型仍可被绕过。

阶段 2：构建真正可重入的 successor 状态机

当前 Quick Dev terminal successor 使用固定 <run>-SUCCESSOR，创建部分目录后崩溃，重试会因为目录存在而失败。这不是简单增加 exist_ok=True 就能解决的，因为必须区分：

这是同一次 successor reservation 的残留；
还是另一次、不同绑定的 successor；
predecessor 是否已经关闭；
successor 是否已经 ready；
latest pointer 是否已经更新。
2.1 状态模型

建议至少支持以下状态：

状态	含义
active	当前 run 可继续
action-claimed	action 已被进程占有
action-stale	claim 过期且进程已死亡
successor-reserved	successor ID 已在事件日志中预留
successor-materialized	successor identity/lineage 已写入
successor-ready	successor 必需输入均已写入
predecessor-closed	predecessor 已绑定该 successor 关闭
pointer-published	latest-successor 投影视图已更新
terminal-completed	terminal result 已发布
blocked	绑定冲突或不可恢复错误
2.2 successor ID

不要继续使用固定字符串。

建议先在 predecessor 的 append-only event log 中写入 successor-reserved，取得唯一 sequence，然后派生：

successorId =
sha256(
  predecessorRunId,
  reservationSequence,
  successorReason,
  expectedBindings
)

重试时：

如果已有未完成的 reservation，继续它；
不创建第二个 reservation；
如果 successor 目录存在且 identity 完全一致，继续；
如果存在但绑定不一致，fail closed；
新一轮真实恢复才分配新 sequence。
2.3 写入顺序

建议事务顺序：

锁定 predecessor/target 的 successor ledger；
读取现有 reservation；
如无 reservation，append successor-reserved；
创建或验证 successor identity；
写入 lineage；
写入所需 handoff/observation；
写入 successor-ready；
关闭 predecessor，并绑定 successor ID；
原子更新 latest-successor pointer；
写入 pointer-published。

关键原则：

predecessor 不应在 successor ready 之前被视为最终关闭；
每一步重试时，“文件存在且内容完全相同”应视为成功；
“文件存在但内容不同”必须失败；
latest pointer 是可重建投影，不是信任根；
信任根是 append-only reservation、lineage 和 closure events。
2.4 GREEN / prior-RED 崩溃窗口

当前还需要关闭“GREEN observation 已写，但 prior-red handoff 尚未写”的窗口。

建议顺序改为：

验证 prior RED；
构造 prior-red handoff；
幂等写入 handoff；
再发布 GREEN observation；
追加 stage transition event。

或者把两者放进同一个 transition manifest，再由 event 引用。重试必须能够识别完全相同的中间状态并继续。

阶段 3：解决 Knowledge 自动刷新与授权冲突

现在的问题是：

Knowledge 同一 selection 的源字节变化会自动刷新 freeze；
freeze hash 一变，implementation authorization 精确绑定就失效；
persistent loop 因此停在 awaiting-implementation-authorization；
“自动刷新并继续”实际上没有实现。

不能通过“自动修改 Maintainer 授权 receipt”解决，这会绕过授权主体。

3.1 分离两个身份

授权应区分：

knowledgeSelectionHash
选择了哪些知识源；
selector、scope、domain、locator 和路径集合；
表示授权范围。
knowledgeContextHash
这些知识源在某一时刻的精确字节；
表示具体执行实例。

Maintainer 基础授权绑定：

implementation contract hash；
authority manifest hash；
Knowledge selection hash；
-允许的自动 successor 类型；
Skill-input contract/version；
禁止 scope widening；
authorizes: []。
3.2 自动刷新链

同一 selection 仅发生源字节变化时，由 canonical Knowledge/Quick Dev producer 发布：

knowledge-refresh-successor-receipt.v1

至少包含：

predecessor context hash；
successor context hash；
selection hash；
predecessor Skill-input receipt hash；
successor Skill-input receipt hash；
changed source path/hash 集；
selectionUnchanged: true；
reason：same-selection-source-byte-refresh；
producer identity；
receipt hash。

有效授权计算为：

effective authorization =
base maintainer authorization
+ verified knowledge refresh successor chain

新的 Acceptance run 仍然绑定精确的 successor context hash，但不要求 Maintainer 为同一 selection 的每次字节刷新重新签一次授权。

3.3 必须重新授权的情况

以下任何变化都必须停止并请求新授权：

Knowledge selection/path 集变化；
scope 扩大；
selector/query 变化；
implementation contract 变化；
authority manifest 变化；
command registry 或受控命令语义变化；
-测试范围、acceptance 条件或风险分类变化；
refresh chain 缺失、断裂或 producer 不可信；
不能证明只是同一 selection 的源字节更新。
3.4 persistent loop 行为

循环应区分：

条件	行为
同 selection、合法 refresh chain	自动创建 binding-derived successor 并继续
selection 或合同变化	停在 awaiting-implementation-authorization
refresh receipt 无效	blocked-invalid-knowledge-successor
当前 run 仍有 live action	等待或报告 active，不创建 successor
stale action 已确认	使用统一 stale recovery
阶段 4：补齐 legacy RED 的回归测试

3c285bcc 已经使 legacy RED fallback 更严格，也支持纯 red-basis.v1.json + red-observed.json，但缺少专门的长期回归测试。

至少覆盖三种输入形态：

当前格式 prior-red handoff；
legacy red-result；
red-basis.v1.json + red-observed.json。

每种格式都要测试：

正确 test hash、execution fingerprint、failure IDs：接受；
test 字节变化：拒绝；
execution fingerprint 变化：拒绝；
failure IDs 变化：拒绝；
缺少 red-basis：拒绝；
非 RED 状态：拒绝；
外部 observation source：成功关闭且不复制历史证据；
terminal 重放：返回同一结果；

两个进程竞争同一 action，只允许一个 claim 成功。
result 文件已存在且字节相同：重放成功。
result 文件已存在但字节不同：失败。
event sequence 并发追加不损坏顺序。

八、最终完成门禁

只有同时满足以下条件，才可以把附件中的问题判定为“修干净”：

Coordinator 不再读取调用者自造的权威证据；
路由不能通过请求字段控制；
所有 action evidence 都能追溯到 persisted run、registry、claim 和 event；
deterministic finalization 会重放完整 receipt；
semantic route 只生成 typed handoff，不越过 Bootstrap 边界；
任一 successor 崩溃点都能重试；
latest pointer 可由 append-only 证据重建；
GREEN 不存在 prior-red handoff 缺失窗口；
同 selection Knowledge 刷新可以自动继续；
scope/contract/command 变化仍必须重新授权；
legacy RED 三种格式有独立回归测试；
8-17 当前 authorization 不再绑定旧 hash；
resume-state 显示 S0–S3 完成；
terminal result 绑定当前合同、当前候选和当前 HEAD；
相同请求二次运行不创建新 run；
GitHub CI 在同一 commit 上通过；
旧失败、旧授权和旧 terminal evidence 未被覆盖或改写。

最重要的一条是：不要把修复方向理解为“再给 coordinator evidence 多加几个 hash”。真正的修复是移除调用者作为信任根，让 coordinator 成为现有 Acceptance 持久化执行控制面的薄编排层。只有做到这一点，3c 修复的局部行为才能进入一个可信、可恢复、可最终验收的完整闭环。
