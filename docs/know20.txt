P0-2 — terminal-full 现在只是 repair validator，不是 implementation terminal validator

这是目前最重要的问题。

implementation-contract.v1.json 把：

repair/round-1/terminal_full_validation.py

定义成最终 terminal_validation。

但这个脚本实际只做：

检查 36/43 ID 集合；
跑 bmad-spec 已有 tests；
跑已有 knowledge tests；
验证 VDD Skill contract；
git diff --check。

而且虽然接受：

--stage source-freeze
--stage exact-cover-negative
--stage recovery-context
--stage composition

args.stage 后面根本没有参与任何分支。所有 stage 跑的完全是同一套旧 tests。

也就是说现在：

--stage source-freeze

并没有验证 source-freeze；

--stage composition

也没有运行真正的 producer → consumer composition。

更关键的是：Exact-cover Skill 还没实现，这个所谓 terminal-full 就已经 passed 了。 composition-receipt 甚至记录了 “75 tests passed”。

这说明它只能证明 VDD repair artifact 自己结构正常，不能作为未来 implementation-complete 的 terminal validation。

正确做法应该分成两个东西：

repair-validation
    → 现在可以 PASS
    → 只验证 VDD repair 本身

terminal-full
    → 真正覆盖 S0~S5
    → implementation 前应该尚不能形成最终 GREEN
    → implementation 后才能证明整个 Exact-cover delivery

VDD 自己也明确要求每个 slice 有真正 RED/negative、GREEN/acceptance command，并在 implementation-complete 前跑 current terminal full replay。

当前 receipt 只有：

但 VDD 当前正式规则明确要求 composition receipt：

所以 repair-closure.json 虽然写了：

这个状态目前还不能按 VDD 自己的规则成立。

P1-2 — allow_stale_catalog 仍然存在过宽旁路

这个问题实际上没有完全修。

现在代码还是：

if current.returncode or (
    (root / relative).read_bytes() != current.stdout
    and not allow_stale_catalog
):

也就是说打开：

--allow-stale-catalog

不仅允许 catalog stale，还同时允许：

knowledge_context_validation.py / _knowledge_locator_core.py 与 current main 不一致。

但现有 test_knowledge_context_validation 测的是：

它没有测试这个 validator-code freshness bypass。

这里建议直接修语义：

allow_stale_catalog
只允许 catalog snapshot stale

绝不能允许 validator implementation stale

也就是 validator 与 current main 的一致性检查不应该受这个 flag 控制。
