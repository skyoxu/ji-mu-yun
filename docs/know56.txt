三、你提出的路径基本正确，但需要四个修正
修正 1：不是任意“重新运行 Locator”，而是 replay frozen selection

自动 successor 不应允许 Locator 根据新排名重新选择候选。

正确顺序是：

从当前已发布的有效 LKG catalog 重放原 Locator request；
使用相同 consumer、policy revision、required modules；
原 accepted path/module/resource-set 作为冻结约束；
重新读取这些路径的当前源码；
重算 read-set source hashes；
验证 selection 投影完全不变；
生成 successor context。

自动路径只允许：

同 path
+ 同 module ID
+ 同 satisfies
+ 同 resource-set
+ 同 consumer
+ 同四维 Knowledge scope
+ 不同 source hashes

如果重新运行 Locator 后排名变化，但旧 selection 仍然存在且满足约束，可以继续使用旧 selection。

如果旧 selection 已经不存在或不能满足 required modules，进入 typed repair，不能自动接受新候选。

修正 2：必须验证使用的是有效 LKG，不是失败的 staging catalog

查询评估失败时：

失败的 staging generation 不得被执行路径读取；
current.json 和 last-known-good.json 不推进；
Locator 继续使用此前验证成功的 published/LKG catalog；
再用当前源码字节重新绑定 selected read-set。

因此执行允许条件应是：

valid published/LKG catalog
AND selection stable
AND authority stable
AND required modules satisfied
AND current selected read-set fully readable and rehashed

不能把：

catalog_publication_invalid
pointer/manifest 损坏
policy/projection 不一致
LKG 非当前 main 的祖先
LKG 输入被篡改

也归类为普通 catalog_stale。

这些仍然必须 hard blocked。

修正 3：同一 path 不代表 authority 没变

这是原方案最需要补强的地方。

假设 selection 仍然选择：

docs/adr/ADR-0048-...

但 ADR 内容被修改了，那么：

selection path 没变；
module ID 没变；
knowledgeSelectionHash 可能没变；
但 authority semantics 已经变化。

因此必须把 source 分成至少两类：

普通执行上下文源

例如：

普通生产代码；
非权威说明文档；
实现细节；
-普通测试代码。

这类同 selection 字节变化可以生成 successor 并继续。

Authority-bearing source

至少包括：

AGENTS.md
Accepted ADR
implementation contract
authority manifest
command registry
-测试身份/测试选择器
Skill contract
Knowledge consumer policy
projection policy
publication policy
-安全和 protected-path 规则

这类文件即使 path/module 不变，只要内容变化，也应：

使原 authorization 失效；或
进入 typed authority repair；
不得仅靠 context successor 自动穿透。

你已经在硬阻断列表里包含 policy、contract、command/test identity，建议再明确加入：

authority-bearing selected source bytes changed
修正 4：“机器验收继续”必须有范围条件

查询质量失败不应该阻塞普通业务实现的机器验收，这一点正确。

但不能普遍适用于 Knowledge 系统自身的改动。

可以 degraded Acceptance 的情况
改动目标与 Knowledge Locator/catalog/evaluator/publisher 无关；
required modules 全部满足；
selected read-set 当前字节已经重新绑定；
authority envelope 没有变化；
Acceptance 的实际检查不依赖失败的查询行为；
protected-path/model routing 没有要求 semantic review。
不能仅用 degraded Acceptance 的情况
修改 Locator 排名算法；
修改 query evaluator；
修改 publication gate；
修改 Knowledge policies/projections；
修改 catalog builder；
修改 TOOL-006 本身或其对应的检索合同；
-当前 Acceptance 的目标就是证明 Knowledge 查询质量。

否则会形成：

Knowledge 查询质量坏了
→ 使用“查询质量失败不阻塞”规则

八、需要修改的 ADR 和合同

这里不能只改 Python，因为仓库要求控制面合同变化更新 Accepted ADR。

ADR-0048

当前规定 stale 结果“按 trusted consumer policy fail closed”。

它留下了按 consumer policy 细分的空间，可以扩展为：

ADR-0050

基本不需要放松。

最终结论

你的方案适合当前仓库，而且应该成为下一阶段 Knowledge 与 Quick Dev 集成的正式模型。

不过我建议把核心原则稍微改写成：

Knowledge catalog 新鲜度不足不阻塞普通执行；当前执行上下文必须对 selected read-set 强一致。查询质量失败阻塞 Knowledge 发布，但不自动阻塞无关实现。selection、authority、contract、command/test 或 authority-bearing source 发生漂移时，仍然阻塞授权与完成。

实施重点不是继续增加 allow_stale_catalog——这个能力已经存在。真正需要完成的是：

把 knowledgeSelectionHash 正式化；
建立 owner-produced successor chain；
把 Maintainer authorization 从“精确 freeze 文件”升级为“selection + authority + contract”；
让每次 run 继续绑定精确 knowledgeContextHash；
更新 ADR-0057，解除 stale catalog 对普通 Acceptance 的全局停止语义。

完成后，Knowledge 将从全局串行门禁变成“严格发布、受控降级、当前字节强绑定”的上下文基础设施，更符合你现在的高速演进阶段。
