  恢复状态还有一个明显风险

  日志中的 world_state 同时保存了：

  - agents_md.text：26,283 字符
  - host_skills.body：22,130 字符

  而同一份 AGENTS 和技能目录已经分别作为 user/developer 内容出现。world_state 正常情况下应只是恢复快照，不应再次作为新消
  息拼入；如果恢复逻辑把两者同时恢复，就会额外重复约 48,000 字符。这正是恢复协议需要重点核查的地方。

  FastCtx 是否是主要原因

  不是启动失败的根因。目前只剩 FastCtx 一个 MCP，taptap-maker 和 sequential-thinking 已经不在配置中。

  FastCtx 有两类开销：

  - 固定开销：它的工具 schema。
  - 动态开销：宽范围 glob/grep/read 返回内容。

  它会放大上下文，但无法解释“46K 输入在 258K 窗口下直接溢出”。这仍然指向网关、Responses 状态续接或恢复重建错误。

  当前最可能的故障链

  启动固定上下文约 29K
  → 多次工具调用重复携带完整上下文
  → 单次上下文增长到约 46K
  → 累计调用输入超过 258K
  → 网关或恢复层错误地按累计值判断
  → context_window_exceeded
  → 恢复后可能重新注入 AGENTS + Skill world_state
  → 后续继续频繁报错

  所以，下一轮最值得修的不是继续压缩根 AGENTS.md，而是：

  1. 检查 aicodemirror 是否正确支持 Responses API 的 previous_response_id、compaction 和 tool continuation。
  2. 检查恢复时是否同时注入 transcript 与 world_state.agents_md/host_skills。
  3. 把实际模型窗口值与网关真实限制对齐。
  4. 将两个工具输出预算从 6000 下调到约 2500-3000。
  5. 从技能发现层真正只暴露允许的技能元数据，而不仅仅禁止自动匹配。
