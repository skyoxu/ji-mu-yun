基于最新 main 的整体更新方案

我重新检查了最新主分支。当前基线已经和本会话前半段明显不同：run-refactor-implementation-acceptance 不再处于“正在实施”状态，而是已经完成全部 S0–S5、确定性终态验证和维护者最终处置，生命周期正式进入 acceptance-passed；但 release、deployment、handoff 和 archived 仍未被授权。

因此，原来的路线：

完成 Refactor Acceptance
→ 创建归档能力
→ 改进 Phase 服务
→ Skill Memory
→ Self-Questioning
→ Curator
→ RL

现在应更新为：

当前可信基线固化
→ 跨工作流证据目录
→ Evaluation Baseline
→ 确定性 Phase 服务优化
→ Skill Memory Shadow
→ Experience Miner + Self-Questioning
→ Skill Curator
→ 离线 RL Internalization
一、最新版本已经完成了哪些前置工作
1. Review 复用身份 P0 已经完成

之前讨论的：

HEAD
+ tracked diff
+ index diff
+ relevant untracked content hash

已经不再是待办。

当前实现已经引入版本化 Git 内容指纹，覆盖：

tracked worktree diff；
staged/index diff；
relevant untracked 文件内容；
Prompt 和运行时身份；
模型、后端、实现字节；
Acceptance commit blob 或 plan-local frozen snapshot；
snapshot drift 的最终成功出口检查。

同一 HEAD 和相同 git status、但内容不同的工作区，现在不会被视为相同输入；旧版身份可以读取，但不能获得新版本的复用资格。

VDD 当前合同也明确要求 dirty candidate 绑定 HEAD、canonical tracked/index diff hash，以及相关 untracked 文件路径和内容哈希。

更新结论：这项从路线图中移除，不再重复建设。

2. Refactor Acceptance 已成为真正可用的 Reward Oracle

当前 Acceptance Skill 已具备：

target-owned persisted run；
start-or-resume；
route-acceptance；
baseline/candidate custody；
frozen knowledge context；
deterministic actions；
Bootstrap bounded routing；
Quick Dev repair handoff；
repair completeness audit；
exact finalized Bootstrap envelope reuse；
manual_pause 和维护者最终 disposition。

它可以拥有完整协调循环，直到 typed acknowledgement、protected boundary、manual_pause 或终态，而不是只报告“需要调用另一个 Skill”后停止。

最新 7 月 31 日处置显示：

最终候选通过六项确定性动作；
Acceptance、Bootstrap companion、plan validator 和 package validation 均通过；
三轮语义预算已耗尽并正确进入 manual_pause；
维护者在确认全部既有 P0/P1 有修复和回归证据后发布 acceptance-passed。

更新结论：不再需要“先把 Acceptance 做完”。现在正是进入证据聚合与 Phase 改进阶段的时间。

3. Bootstrap 已经具备部分 Archivist 和 Miner 基础

Bootstrap 当前已经有：

append-only process events；
可再生 lease 和 registry；
lineage family；
两轮默认、三轮硬上限；
repair delta；
list-runs、inspect-run、inspect-lineage；
historical policy replay；
build-review-baseline；
review history index；
cost calibration candidate；
finalized-run replay；
exact candidate binding；
validation envelope v3；
exact Acceptance reuse。

build-review-baseline 会重放 finalized runs，构建 append-only 历史索引和成本校准候选；这些输出明确 authorizes=[]，不能产生 clean、acceptance、release 或 done。

Bootstrap Skill 也明确规定，历史基线只能作为成本和运营观察，不能自动更新已晋升校准，也不能成为当前语义真相。

更新结论：新的 Run Archivist 不能重复实现 Bootstrap Registry、History Index 或 Cost Baseline。

4. Quick Dev 到 Acceptance 的修复闭环已经建立

Quick Dev 现在会在 P0/P1 修复完成后：

生成标准 repair-review handoff；
保留 baseline/candidate manifests；
保留 changed files、direct consumers、targeted tests；
生成 root-cause callsite inventory；
保存 producer/consumer composition receipts；
立即调用 Acceptance-owned audit-repair-completeness；
不自行选择 Acceptance 路由；
不自行创建 Bootstrap successor；
不修改稳定 lineage family。

更新结论：Experience Miner 的第一批高价值数据，不应只来自原始日志，而应优先消费这些结构化 repair handoff 和 completeness 结果。

5. 知识系统已经有可复用的评测模式

知识系统现在不是简单目录，而是：

immutable generation；
current/LKG；
consumer policy；
snapshot-bound evaluation；
adapter decision gate；
108-query evaluation；
failed-build evidence；
explicit publication 和 retention。

maintain-knowledge-base 只维护派生知识，不修改源文件；发布 CLI 负责 108-query evaluation、原子 current/LKG 和失败证据。

当前 query suite 已按 consumer、类别、期望路径、最大排名和 source terms 定义稳定的正例集。

更新结论：后续 Phase Evaluation Suite、Skill Candidate Evaluation 和 Shadow Replay 应复用这种“快照绑定、固定样本、不可自动授权”的设计。

二、对三个新 Skill 的最新调整

仍然建议保留三个独立 Skill 包，但第一个 Skill 的定位需要调整。

1. 不再建议做“复制型 Run Archivist”

原来的名称：

archive-phase-run

容易让人误解为：

把所有 Run 搬到统一目录；
复制 Bootstrap/Acceptance 原始证据；
建立新的生命周期权威；
把现有运行目录统一重写。

这与当前仓库已经形成的“生产者拥有自己的 append-only evidence”冲突。

更新后的推荐名称
maintain-phase-run-evidence-catalog

或：

index-phase-run-evidence

它不是保存所有原始证据，而是建立一个跨工作流派生证据目录：

VDD 原始证据仍归 VDD 所有
Quick Dev 原始证据仍归 TDD Adapter 所有
Bootstrap 原始证据仍归 Bootstrap Control Plane 所有
Acceptance 原始证据仍归 Acceptance target-owned run 所有

Evidence Catalog
只记录它们的位置、类型、哈希、关系和可用性

因此更准确的角色名称是：

Run Evidence Catalog / Evidence Custodian，而不是集中式 Archive Authority。

2. Experience Miner 保持独立

推荐继续使用：

mine-phase-run-experiences

它读取统一 Evidence Catalog，按需回到各生产者的正式证据，不直接扫描整个仓库猜测运行状态。

3. Skill Curator 保持治理一级入口

推荐继续使用：

curate-phase-skill-candidates

它仍是独立显式治理入口，但第一版是：

确定性状态机
+ 固定 Evaluation Suite
+ Shadow Replay
+ LLM 建议
+ 人工批准

而不是自主修改 Skill 的 Agent。
