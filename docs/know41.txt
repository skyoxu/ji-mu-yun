P1-1：当前 S1 的 candidate drift 语义有一个逻辑冲突

这是最需要先修的一点。

文档现在写：

GREEN consumes only a matching RED summary；Candidate drift creates a successor preparation and does not reuse stale stage evidence.

问题是：

RED candidate A
→ implementation
→ candidate B
→ GREEN

TDD 的正常实现本来就必然导致 candidate 改变。

所以如果：

candidate change = drift

那正常的 RED → implementation → GREEN 每一次都会把 RED 判 stale。

这里应该拆成两个 identity：

RED basis identity
=
failure intent
+ test selector
+ contract
+ validator
+ pre-implementation candidate

然后：

implementation successor
=
RED summary hash
+ new candidate identity
+ declared write-set delta

GREEN 应要求：

same RED lineage
same failure intent
same test selector
same contract/validator semantics
+
current post-implementation candidate

而不是要求：

GREEN candidate == RED candidate

真正的 drift 应该是：

contract changed
validator changed
test selector changed
RED test changed outside allowed transition
undeclared write-set changed
authority changed

而正常 production implementation change 不是 drift，而是 successor。

这个一定要先写死，否则 stage recovery 做出来会不停自我失效。

P1-2：self-hosted migration 现在存在一个自举循环

计划说：

legacy one-shot lifecycle evidence 只能 read-only，新的 staged evidence 由新流程产生。

但是现在真正执行 S0/S1 的 Quick Dev 本身，还是旧的一次性 lifecycle。

因此会出现：

要实现 staged Quick Dev
     ↓
需要 staged Quick Dev 执行这个计划
     ↓
但 staged Quick Dev 还没实现

建议明确一个一次性的 migration bridge：

S0
旧 adapter 执行 targeted RED/GREEN
→ 安装 stage-summary primitive


S1
旧 adapter / migration bridge
→ 安装 route/resume stage machine


CUTOVER


S2
新 staged adapter
→ dogfood 8-17 acceptance-coordinator
→ RED / implement / GREEN / refactor 分离执行


terminal-full
→ 只认可新 staged path
→ implementation-complete

也就是说：

允许旧 harness 帮你造出新 harness，但旧 harness 不能证明最终新 harness 已完成。

最终 completion 必须由 S2 dogfood + terminal-full 证明。

这和你现在写的“8-17 是第一个 dogfood consumer”完全一致，只需要把 cutover 边界补明确。
