整体评价：方向正确，而且针对上一轮 4 小时 / 1.37MB / 101×3 segment 的浪费，抓到了真正的结构性原因。 我会给这个方案 8.5/10。它不是简单“少喂上下文”，而是在把 Review 从“目录驱动”改成“证据闭包驱动”，这一点是对的。

而且有不少内容其实不是推翻现有设计，而是在把现有设计真正落实到控制器：当前 Bootstrap 标准本来就要求 implementation conformance 使用 smallest complete consumer closure、完整读取选中 artifacts、禁止 sampling；也已经规定 segmented child 只负责 parent-assigned segment，process events 是 lease authority，Artifact View 使用冻结 snapshot。

我认为必须调整的 5 点
“默认单 reviewer，高风险再三角色”不要直接做成 Bootstrap 内部策略。
这是当前方案最大的架构问题。现在 durable Bootstrap contract 明确规定：一次 complete review 必须包含 blind_hunter + edge_case_hunter + acceptance_auditor 三个隔离 discovery roles；profile 里 bootstrap-implementation-conformance.requiredLayers 也是这三层。
更合适的是让 Acceptance 决定是否需要 Bootstrap：
deterministic_only → 不调用 Bootstrap
或
full_implementation_conformance → Bootstrap 仍按三角色执行。
当前 Acceptance 本来就拥有 decide-bootstrap / route-acceptance，并能选择 deterministic_only / focused_repair_verification / full_implementation_conformance / manual_pause。
如果确实想引入“单 acceptance reviewer”，应该把它定义成新的、非 Bootstrap complete-review 的 non-authorizing semantic check，或者正式修改 ADR + standard + profile，不能静默改变 Bootstrap 的含义。
确定性 preflight 不要把 source-freeze / exact-cover / shard / retry 硬编码进通用 Bootstrap。
你的“机器先验”原则完全正确，但这些是 8-13 当前计划的具体 commands。Bootstrap 应该继续只执行 Acceptance/implementation contract 投影出来的 required-check。当前 Skill 已经明确要求 implementation conformance 绑定每个 plan-mandated deterministic check。
即：
contract/registry → required-check set → Bootstrap deterministic preflight，而不是 Bootstrap 自己认识 exact-cover。
“合同片段”要非常慎重。
changed implementation 可以 diff-first，但 normative authority 最好不要由 reviewer 自己截片。若只传部分 SPEC/contract，必须由 parent builder 产生：
source path + full source hash + inclusive range + extracted bytes hash + inclusion reason。
否则很容易重新出现“闭包看似小，但把反例条件切掉”的问题。当前标准要求 selected required artifacts complete、sampling prohibited，所以我更倾向于：小合同直接整文件；真正超大合同才用 controller-owned hash-bound range projection。

implementation-complete 的位置需要改。
你最后的简化流程里写成：
模型 review → 机器闭合 → implementation-complete handoff。
按当前 authority，这个顺序不对。implementation-complete 是 Quick Dev 的输出，是 Acceptance 的入口前提；Bootstrap implementation-conformance 属于 Acceptance 后续可能调用的语义验收，不应该反过来生成 implementation-complete。Acceptance 当前也明确消费 implementation-complete VDD/Quick Dev target，然后才决定是否路由 Bootstrap。
应改成：

Quick Dev implementation-complete → Acceptance deterministic evidence → decide-bootstrap → [Bootstrap if required] → Acceptance finalization

你列出的 5 个“控制面缺陷”判断基本准确，而且其中 3 个其实已经违反现有标准，不需要再发明新策略。
现有标准已经要求 segmented child 只处理 parent-assigned segment、snapshotPath 按绝对 run-dir 语义解析、access proof 绑定 executable identity、dead event-backed PID 先追加 stale event 再 rebuild lease。
因此 segment 越界 / 相对路径错误 / executable identity 人工漂移 / lease 残留 应定性为现有控制面 implementation defects，直接修代码和回归测试，不必再升级成新的架构概念。

这样既能大幅减少模型调用，又不改变 Bootstrap 自己的 authority semantics。

控制面则单独做一个 bounded hardening：

immutable segment descriptor
→ one canonical segment_payload_hash
→ materialized segment-only snapshot
→ controller-projected absolute path
→ access-proof-owned executable identity
→ child attempt
→ terminal process event
→ automatic lease reconciliation
→ bounded segment retry
→ exact receipt fold

特别是 payload mismatch，我建议不要只“调查为什么 mismatch”，而是直接消除多套 identity 计算：assignment、prompt request、child receipt、parent validation 全部调用同一个 canonical segment projection/hash 函数。然后 mutation test 分别改 path、offset、line range、artifact hash、segment order，必须全部稳定拒绝。这会比继续修具体 mismatch case 更可靠。

关于“1.37 MB / 101 segments × 3”问题

你的目标“不要再全量三角色重复消费整个 tree”是对的，但正确优化不是：

三角色 → 单角色

而应该首先是：

1.37 MB 错误闭包 → 例如 80–200 KB 真正的 minimal complete closure

如果 closure 已经从 101 segments 缩到 8 个，即使仍是三角色，也只是 24 个 segment attempts；再配合 deterministic-only route，很多普通任务甚至会是 0 个 Bootstrap model call。

这比削掉两个 reviewer 更符合现在这套系统的 authority 设计。

最终评审结论

我建议 批准这个方案，但按“策略层 + 控制面层”拆开实施，并修改 review-intensity ownership。

策略层重点不是改 Bootstrap 三角色，而是：

Acceptance diff-first scope builder + deterministic-first routing + minimal complete closure + Bootstrap only when typed policy requires。

控制面层重点是：

segment 强隔离 + canonical payload identity + absolute snapshot projection + executable identity 自动继承 + automatic lease reconciliation + bounded retry。

验证标准也赞成你提出的：最后必须拿一个接近 8-13 规模的场景做 regression。成功条件不要只写“测试通过”，而应直接量化为：

无越界读取 + 无 stale lease + 无人工 executable 重填 + mismatch 有界终止 + deterministic failure 零 reviewer call + closure 显著小于 whole plan + Bootstrap-required 时仍完整覆盖 closure。

做到这里，我会认为上一轮暴露的策略性浪费和控制面 operability 问题都真正闭合了
