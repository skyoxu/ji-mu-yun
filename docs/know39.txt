看完最新 Acceptance production code，再对照你附件的方案，我的结论是：

方案整体非常适合当前最新版 Acceptance，而且优化方向抓得比继续优化测试本身更准。

但我建议按 “4 项直接采用 + 3 项修改后采用 + 2 项不要做重” 来落地，而不是原文全部照搬。

附件自己也给出了很有说服力的原因：本轮 Acceptance 墙钟约 7 小时 17 分钟，而 terminal-full 真正执行只有秒级，时间主要耗在 artifact 重建、binding drift、人工路由和恢复。 这说明现在的瓶颈已经从“验证能力不足”转成了控制面编排效率不足。

最重要的 P1-1：附件判断是对的，而且我在当前代码里验证了

现在 8-15 的 terminal_validation.py 发布：

{
  "schema_version": "quick-dev-implementation-complete.v1",
  "plan_id": "...",
  "contract_hash": "...",
  "command_registry_hash": "...",
  "terminal_command_id": "terminal-full",
  "validated_command_ids": [...],
  "results": [...],
  "authorizes": ["implementation-complete"]
}

确实没有 candidate manifest / candidate revision / candidate binding。

所以附件说的 candidate A receipt 理论上可能和 candidate B projection 组合，不是误报。

我建议不要只加一个裸 candidateBindingHash，而是把它固定成类似：

candidate_binding =
  candidate content manifest identity
  + candidate custody/snapshot identity
  + terminal runner identity

Acceptance admission exact-match。

这是这次优化里优先级最高的一项。

P1-2：deterministic_only 去 semantic child，非常适合当前版本

当前 Acceptance 的 SKILL.md 仍规定，在 start-or-resume 之前无条件准备 Skill Input receipt、启动 semantic consumer，然后 require-ready；acceptance_cli.py 的 start-or-resume 也强制要求 --skill-input-receipt 和 --skill-input-contract。

这和现在已经建立的：

supervised
+
deterministic_only
+
no Bootstrap

实际上有点矛盾。

你的附件提出：

deterministic_only 使用 deterministic source-sufficiency receipt；semantic child 只服务 semantic route。

我赞成。

但要加一个重要限定：

不能让 caller 传 route=deterministic_only 就跳 semantic gate。

应该是：

freeze candidate
→ changed-set / closure
→ required checks
→ deterministic trigger/route projection
→ route == deterministic_only
   ? deterministic source-sufficiency
   : semantic Skill-input

也就是说route 必须先由 Acceptance 自己的机器证据决定。

P1-3：bundle/context 单一 authority，也确实命中当前实现

当前 compact_vdd_projection.py 接受一个独立的 knowledge_context 输入；而后续 prepare-run 又可以独立传 knowledge_context_path。

因此附件指出的：

projection bundle = context A
prepare-run        = successor context B

确实存在结构上的漂移窗口。

建议完全按附件修：

bundle owns context reference
        ↓
prepare-run only consumes bundle

context successor：

new context
→ new bundle
→ derived successor run

不能现场 override。

P1-4：finalization 幂等 replay，也是对的

当前 matrix_phase.py 的 publication helper 使用 "x" 创建文件，文件存在直接：

InputError("result publication is append-only")

publish_final_result() 也直接走这个路径。

所以：

同一 binding
第一次：SUCCESS
第二次：文件已经存在 → ERROR

对于 durable coordinator 来说确实不合理。

应该变成：

exists
  ↓
read existing
  ↓
same complete binding?
   ├─ yes → replay existing result
   └─ no  → conflict

这不违反 append-only。

相反，它才是真正的 append-only idempotency：

不覆盖、不新建第二份、不制造假失败，只重放已经存在的 immutable success。

附件这一点我完全支持。

有三处我会修改附件方案

第一处是 catalog_stale。

附件希望：

catalog_stale 不阻断验收。

这个说得太宽。

当前 Acceptance 故意规定 catalog_stale 输出 knowledge-maintenance-required，并禁止 Acceptance 自动发布 Knowledge；需要 maintainer 明确进入 knowledge owner。

更安全的规则应该是：

catalog stale
+
Locator proves:
  selected knowledge sources unchanged
  source bytes unchanged
  read-set unchanged
        ↓
automatic derived-context successor

否则：

actual source/catalog authority changed
→ knowledge-maintenance-required

即：

允许自动 refresh 派生物，不允许 Acceptance 自动修改 Knowledge authority。

第二处是附件写的：

coordinator 不自动调用 Bootstrap。

对于 deterministic_only 完全正确。

但作为“通用 Acceptance coordinator”不能写死。

应该是：

deterministic_only
→ no Bootstrap


focused/full
→ typed Bootstrap handoff
→ 按 policy / acknowledgement boundary 继续


manual_pause
→ stop

换句话说：

Coordinator 不擅自启动语义模型，但也不能截断已经由 Acceptance 确定的 Bootstrap-required route。

否则以后 unattended mode 会被这个优化破坏。

第三处是 hash 优化里的 environment。

附件提出 PATH、TEMP、USERPROFILE 等不要成为高噪声 hard binding。

方向对，但 PATH 不能全局直接删除。

因为如果：

python
git
dotnet
node

通过 PATH resolution 找 executable，PATH 就可能改变实际执行对象。

更好的原则是：

Environment binding 由 command descriptor 明确声明 behavior-affecting allowlist。

如果 executable 已经解析成绝对路径并绑定 executable hash，那么 PATH 可以降级；否则保留。

Coordinator 本身我非常赞成，但不要再造一个重型服务

附件的核心状态机：

resolve
→ handoff validation
→ context
→ projection
→ skill input when needed
→ start/resume
→ DAG
→ stale recovery
→ finalization
→ package validation

和当前 Acceptance 的代码结构非常匹配。

因为现在其实已经有很多原料：

persisted run；
append-only events；
action claim；
PID/process identity；
stale-action recovery；
successor attempts；
exact action receipt reuse。

所以不要重写 execution control。

只缺上面的一层 coordinator。

我建议第一版就一个：

acceptance_cli.py run-coordinator

特性：

one-shot
reentrant
idempotent
same binding → resume/replay

不要先上：

background daemon
watch service
persistent supervisor process

否则刚把 Acceptance 从 7 小时人工调度瘦下来，又会造一个新的运行时系统。

后台 supervisor 真有 unattended 需求时再做 M2。

还有一个地方可以直接从附件阶段二删掉：

package validation 本身不需要特别做幂等改造。

当前 validate_package() 本来就是纯 read-only deterministic function：读文件、检查 REQUIRED 和 fixture catalog、返回 findings，没有 publish side effect。

需要幂等的是：

coordinator 对 package-validation result 的记录/replay

不是 validator 本身。

我建议你把实施顺序改成这样
M0  Safety / identity
    Quick Dev candidateBindingHash
    Acceptance exact-match handoff
    bundle owns knowledge context


M1  Deterministic fast path
    deterministic route projection before semantic child
    deterministic source-sufficiency receipt
    deterministic_only = zero semantic child / zero Bootstrap
    safe catalog-derived refresh


M2  Idempotency
    finalization identical replay
    receipt/import replay
    owner-scoped latest successor pointer
    hash hard-blocker consolidation


M3  Coordinator
    run-coordinator
    execute/resume DAG
    stale successor recovery
    replay completed steps
    timing/intervention telemetry


Later
    optional unattended supervisor

这样比附件原来的“阶段一/二/三”再稳一点，因为 candidate identity 应该放第一阶段，不该等第二阶段。

最终判断

我会给这份方案大约 85–90% 的认可。

最值得实施的是：

candidate-bound Quick Dev handoff + deterministic-only 无模型路径 + bundle/context 单一 authority + idempotent finalization + thin resumable coordinator。

这五件事正好针对你这次 7 小时验收真正浪费时间的地方，而且不需要重做 Architecture、不需要重新设计 lifecycle，也不需要继续增强 Bootstrap。附件自己也明确把这些列为非目标，这是正确的边界。
