主要问题

1. --target 并未真正决定被验证的 Skill 包。

默认能力配置指向 Acceptance 的 acceptance_cli.py。包装器调用它时，只传入 validate-package，没有传入目标路径；Acceptance CLI 最终验证的是它自身所在的包。

因此，命令即使声明 --target .agents/skills/vdd-execution-plan，实际也可能是在检查 Acceptance 包，然后将 VDD 的目录哈希写入成功回执。“回执绑定了目标”不等于“验证器检查了目标”。

来源：包装器实现、Acceptance CLI。

2. 正反探针结果是直接填写的，没有真正执行。

replay-package 中直接构造：

{"probe_id": "detached-positive", "status": "pass", "exit_code": 0}
{"probe_id": "detached-negative", "status": "expected-failure", "exit_code": 1}

没有生成独立合法/非法包，也没有分别调用验证器并检查结果。--probe-mode 主要被记入命令记录。

这不满足需求中“必须证明验证器能够区分合法和非法 detached fixtures”的要求。对应代码

3. 能力替换和内容漂移没有被可靠阻断。

目前主要检查的是：入口位于配置声明的根目录内、文件存在，以及运行退出码为零。

但实现没有把验证器当前哈希与可信的预期身份比较；version 甚至直接使用命令 stdout。能力配置中的 probe_args 也没有被实际采用。

我的隔离复现结果：

输入情形	实际结果
不存在的目标包 + 永远退出成功的替代验证器	返回 pass
修改该验证器内容后再次调用	仍返回 pass

这直接说明缺失目标、验证器替换及漂移防护没有达到需求预期。回执记录新哈希，只能描述运行了什么，不能证明它是允许的验证器。

4. 回放矩阵没有执行案例，而是复制预期结果。

replay-matrix 的核心逻辑是：

"status": "pass",
"observed_result": case["expected_observation"]

没有加载 stable/candidate 两套实现，也没有运行六类验证场景。每个案例的证据都指向同一份完成报告，而非各自的执行输出。

我在临时矩阵中填写不存在的验证面和任意预期字符串，程序仍返回：

status=pass
observed_result=invented-observation

因此，该矩阵目前是结果格式生成器，不能作为稳定版/候选版行为对比的证明。实现、归档矩阵回执

5. 终端验证器不能识别上述“格式正确、行为未验证”的情况。

终端确实会重新执行包装器，并比较 stdout 与保存回执，但包装器可以确定性地再次生成相同的预填结果，所以这一检查仍可能通过。
