 2. 你的设计方向正确，但需要调整权威边界

  我赞成目标，但不赞成“由子 LLM 自主决定读取哪些文件”。更稳妥的协议是：

  主进程确定任务、权威顺序、允许文件和哈希
    -> 子进程只读取该白名单并生成 recovery-context.v1
    -> 主进程做 schema、哈希、任务身份和新鲜度验证
    -> 主进程重新加载当前常驻上下文
    -> 注入一份精简任务恢复上下文继续执行

  关键规则：

  - 常驻上下文不进入恢复包，由主进程按当前版本重新加载。
  - 子进程不能扩大文件范围，也不能扫描日志寻找“可能有用的信息”。
  - 工具调用、原始工具输出、assistant 闲聊全部剔除。
  - 保留工具结果的耐久结论，例如退出码、测试状态、证据路径和哈希。
  - 自由文本日志不是恢复权威，但可以作为结构化 JSON 引用的诊断证据。
  - 缺少必需来源、哈希不匹配或状态过期时必须 fail closed。

  这也符合本仓现有规则：/C:/jimuyun/PhaseA.Platform/AGENTS.md:43 要求服务端选择并冻结来源、阻止子进程扩张上下文；/C:/jimuyun/docs/
  architecture/phase-service/prototype-routes-and-recovery.md:33 已定义确定性的八级权威顺序。

  需要稍微修正“严禁从日志恢复”：应当禁止从自由文本执行日志推断任务状态，但不能按目录名一刀切。本仓部分当前结构化状态位于 logs/phase-a-
  innernet/workspaces/**，而且修复路线允许引用最新诊断证据。应按 schema、authority、hash 和生命周期判断，不按文件是否位于 logs/ 判断。

  你的方案更适合作为一层新的“结构化任务 checkpoint + 语义 handoff”，放在 Codex 原生 resume 之上。若在 Phase 平台落地，会触及受保护的
  CodexHostedProcessCommandFactory 或共享 LLM 入口，实施前需要单独批准并补充 ADR、schema 和恢复测试。
