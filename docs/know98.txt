先校正一个关键边界：S6 当前生产代码扫描历史 run，正是 S6 要通过 TDD 修复的目标缺陷；VDD repair 不应提前删除它。进入 Quick Dev 前必须做到的是：S6 RED 自己提供显式 lineage 输入、不读取真实历史日志，并因当前生产代码没有消费显式输入而稳定变红。

下面是完整、干净的修复方案。

一、修复目标

最终形成一个新的代码候选提交 REPAIR_SHA，满足：

六个 RED 都是独立、可执行、单一语义缺口。
六个 RED 都调用合同声明的真实生产函数。
RED 只修改 selector、合同和执行控制面，不修改目标生产行为。
GREEN/REFACTOR 的解析结果明确包含同一个 RED selector。
S6 RED 使用显式 lineage 输入，不扫描真实日志。
Quick Dev 的允许修改路径足以完成每个 GREEN。
生命周期 runner 可以正常启动。
external review 与 maintainer authorization 绑定 REPAIR_SHA。

四、第三组：确保 GREEN/REFACTOR 真实执行同一 selector

修改 stage_command.py，固定非 terminal 阶段顺序：

根据 contract 解析 RED selector。
解析 regression selectors。
构造最终 pytest selector 列表。
执行相同 RED selector 和 regression。
pytest 成功后调用 artifact owner 生成阶段工件。
任一步非零立即返回，不产生伪成功。

核心结构：

red_selector = resolve(selected["tdd"]["red"]["test_selector"])
regressions = resolve_all(
    selected["tdd"]["regression"]["test_selectors"]
)
selectors = [red_selector, *regressions]

test_result = subprocess.run(
    [sys.executable, "-m", "pytest", *selectors],
    ...
)
if test_result.returncode != 0:
    return test_result.returncode

return run_artifact_owner(...)

这样即使 owner 当前尚未完成，GREEN 命令也已经真实重跑相同 selector。

增加一个无副作用的解析模式，例如：

--resolve-selectors

输出：

{
  "slice_id": "S6",
  "stage": "green",
  "red_selector": ".../red_s6_terminal_producer.py",
  "pytest_selectors": [
    ".../red_s6_terminal_producer.py",
    ".../test_s6_terminal_red.py"
  ]
}

合同验证器使用此模式检查 GREEN 和 REFACTOR，不要只通过阅读字符串推断。
