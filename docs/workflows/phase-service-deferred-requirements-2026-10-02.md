# Phase 服务层暂缓需求说明

版本：2026-10-02。适用仓库：`skyoxu/ji-mu-yun`，基于 main `3b2d677aa2c0bd4c6ef12e1fdbf3414ac9979ad4` 与本次普通项目 Runner/业务链路验收修复。

## 范围与判断口径

维护方式为 AI 主导、一人维护、Windows 单机部署，以一次性受控执行和浏览器启动/中止/恢复为主。本文件整理 Phase 服务层后置扩展，记录需求原因、暂缓原因、实际内容与重新启动条件。不以多人协作、长驻模型会话或大规模分布式平台为当前设计前提。

“暂缓”表示保留扩展价值，出现具体触发条件后再实施；“不用重复实施”表示已有实现或已有指定计划。两者分开处理。本文件不是对所有旧 B/C 编号重新开工，也不自动授权实施用户沙箱层功能或创建 VDD 计划。

8-24 的身份、隔离与恢复底座已并入 main，已有权威源为 `_bmad-output/specs/spec-phase-b-c-identity-isolation-workspace-recovery/SPEC.md`、配套执行契约和 ADR-0061。旧文档里有关这些底座的待办须以当前代码与机器验收为准，不能再次列为未实现的新需求。

## D1：服务入口、工具和 MCP 的统一能力目录

**需求原因**：新增入口时，需要明确谁拥有能力、入口如何调用、依赖什么运行环境、证据位于哪里，以及 browser/API/CLI 是否可调用，防止模型根据一个工具名称自行扩大权限。

**暂缓原因**：现有 `RouteActionDescriptors`、`RouteModuleContracts` 和 route preflight 已覆盖主要服务路由。当前一人维护、入口有限，重建跨平台目录会产生并行清单和同步成本。已有工具链 Skill 目录计划不能重复计入此项。

**实际内容**：只为 Phase 运行入口增加可查询的投影：owner、调用入口、依赖、证据引用、适用工作流、输入/输出边界、权限与网络条件。外部工具/MCP 启用前有明确允许清单；未声明工具保持不可用。投影消费既有 route catalog 和控制面规则，不自行成为新授权源。

**重新启动与验收**：实际新增工具先补该入口最小声明；仅当多个入口需要统一查询时建聚合目录。用允许/拒绝调用、未知依赖和不可用工具负例证明边界，目录记录不能代替真实运行探测。

## D2：平台派生配置 doctor/repair 与生命周期界面

**需求原因**：生成配置、能力 manifest、派生索引可能与权威源发生漂移，需要可定位和安全重建的方法。

**暂缓原因**：当前资产有限，定点检查与受控重新生成已经可维护。统一 doctor、安装/升级/禁用界面及回滚框架会增加维护面；纯 Skill 包检查、Evidence Catalog 重建/LKG 恢复已由指定工具链计划覆盖。

**实际内容**：限定平台运行资产，提供只读诊断、漂移 diff、dry-run 修复计划、确定性重建、范围受限的清理与回滚。按账号/项目/run 边界工作，不能覆盖用户源文件或改写历史验收。生命周期 UI 消费相同命令与权威记录，避免自行维护一份状态。

**重新启动与验收**：至少出现重复漂移或多次人工修复后再实现。证明 dry-run 零写入、重复执行幂等、边界外文件不变、失败可回退；先命令后界面，不为一人维护增加审批层级。

## D3：证据/ledger/readiness 格式统一与资源索引扩展

**需求原因**：跨 route 的 evidence bundle、route ledger、acceptance、资源 manifest 和 sidecar 需要稳定交换与查询，资源替换时也需要来源和引用关系。

**暂缓原因**：8-24 已有 DB 绑定、脱敏、校验和恢复设施，当前 native 数据与 sidecar 能支持主要路由。整体迁移统一格式不能增加第二套完成状态或 snapshot/current/cache/LKG 权威。当前 UI 最小来源与闭环证据的缺口属于业务验收必要项，不能以“全量统一暂缓”为由放过。

**实际内容**：在实际消费者需要时增加适配器/validator：账号、项目、run、correlation、hash、新鲜度、保留期、证据定位和允许范围；整合 `.cs/.tscn/.tres` 的可重建资源索引与引用信息；对齐 readiness 读模型。保留原有存储、恢复和历史读回；不统一搬迁所有旧 sidecar，不要求外部格式接管项目文件。

**重新启动与验收**：以具体跨消费者错误或资源追踪需求启动。覆盖旧数据兼容、来源变化失效、引用缺失、重复/孤立记录、越界路径和错误账号负例；readiness 标绿必须指向当前 validator、时间与机器证据。

## D4：Type-kit JSON 执行契约

**需求原因**：游戏类型扩展若需独立发布或由外部数据驱动，可用版本化 JSON 表达条件能力、首目标边界、恢复输入、验收 marker 和 stale 规则，并校验说明与执行定义一致。

**暂缓原因**：当前 Markdown 与原生 C# 类型契约已经存在，专用 route 也已实际消费它们。只为格式统一迁移 JSON 会产生新的解析、兼容和双份权威风险，现有维护规模尚不需要。

**实际内容**：确有独立发布需求后定义 JSON schema、版本/hash、条件能力与适用性，声明恢复及验收字段，并实施 Markdown/JSON/C# 消费一致性校验和明确迁移。JSON 只能成为明确指定的权威，不能与现有 C# 契约同时各自决定执行行为。

**重新启动与验收**：新增类型先补现有契约与轻量一致性检查；只有数据发布成为瓶颈再迁移。测试缺失 marker、过期契约、条件能力不适用、恢复输入不足，以及旧项目兼容；不把 JSON 的存在当作类型执行已支持。

## D5：扩展诊断、经验规则和可选帧捕获

**需求原因**：重复 Godot/C# 故障适合变成稳定 rule id、severity、修复提示和误报 fixture；视觉问题可能需要图像证据；成熟经验可供后续项目复用。

**暂缓原因**：既有诊断和失败读回已经存在，当前适合按实际故障补少量规则。预先建设泛化诊断框架、自动经验晋升或帧捕获流水线，会增加错误规则、环境依赖和维护成本。用户沙箱 MEMORY 的自动维护不在本文件范围。

**实际内容**：仅把反复出现的实际故障加入诊断库，具有明确修复提示和正/负 fixtures；平台记录通用 pitfalls 的分发版本、项目经验候选格式和人工晋升规则。可选帧捕获需校验采集来源、run 绑定、图像引用和执行稳定性；某个 route 若明确要求视觉证据，它的必要捕获不能延期。

**重新启动与验收**：以真实复现或 route 的视觉验收需求启动。先一条可靠规则，再扩展目录；覆盖误报、无法采集和来源过期，不以捕获成功替代业务验证。经验晋升由单一维护者明确操作即可。

## D6：身份产品、账号物理清除和审计检索

**需求原因**：对外开放后，可能需要实际身份提供方接入、登录/找回/邀请等界面、明确的账号数据清除，以及按 run/模型/时间筛选审计记录和导出。

**暂缓原因**：8-24 已完成主体、角色、凭据生命周期与账号边界；当前受控账号场景可继续使用既有发放方式。OIDC-first 兼容方向已有决定，不重开“用什么身份模型”的选型。登录产品、物理删除和复杂审计界面没有当前使用压力。

**实际内容**：在既有 Principal 映射上接入选定身份提供方，处理绑定、退出、吊销和兼容迁移；根据真实产品需求再确定是否提供自助注册/邀请/找回。账号物理清除需处理项目、历史证据、保留期、受保护快照与凭据，并留下合适审计。审计查询增加所需筛选、分页和受权限控制的导出，沿用既有脱敏规则。

**重新启动与验收**：对外登录或明确清除/审计需求出现时启动。测试拒绝、禁用、撤销、跨账号、分页稳定性和脱敏；物理清除与项目软删除严格区别，不能用立即删除替代已有 30 天恢复规则。

## D7：存储后端、多节点 Worker 与更强隔离

**需求原因**：跨机器恢复、容量扩展或更高风险执行可能需要对象存储/另一存储后端、跨节点执行及 Windows Sandbox/容器/VM 等更强隔离。

**暂缓原因**：当前 Windows 单机已有真实低权限身份、ACL、Job Object 与 durable Restore。本地目录是可用的第一后端；未出现必须跨节点或换后端的证据。增加分布式协调与第二运行环境会明显扩大一人维护成本。

**实际内容**：保留账号/项目/逻辑路径绑定、immutable manifest、hash 校验、quota、retention、幂等恢复和 staging/publication/quarantine 契约，新增最小存储 provider 和迁移回退方案。跨节点 Worker 保留 lease fencing、取消/超时、证据归属及重启恢复语义；更强隔离等级明确文件/网络/凭据边界和容量成本。不得自动迁移宿主凭据或复制未经声明的秘密。

**重新启动与验收**：容量、恢复目标或真实执行风险要求现有边界之外的能力时，再以一个明确场景试验。先做后端 round-trip 和故障恢复，或单个隔离等级验证；不预建 Kubernetes、多机调度或多个后端。

## D8：统一遥测、可重建索引与运营看板

**需求原因**：跨 route 关联失败、执行证据和恢复动作，可减少定位时间；项目规模增长后可通过看板查看当前就绪与最近故障。

**暂缓原因**：8-24 已有基础事件与审计，日志、DB 和当前 API 足以支持一人运维。全面事件重构、跨域派生索引和看板在当前规模收益有限，容易让派生状态误当作权威。

**实际内容**：仅统一实际消费所需的最小 correlation/account/project/run/event/time 字段，增加可重建的 run/route/诊断/恢复投影与索引。看板显示来源、时间和 stale 状态，可回指权威 DB/文件，不自行标记完成，不引入跨层 snapshot 或 current 权威。

**重新启动与验收**：多次排障必须手工跨来源拼接、且索引能实际节省时间时启动。先关联查询，再派生索引，最后界面；验证可从权威重建、来源缺失则 unknown、来源变化则 stale，旧记录不重写。

## 可以后置的小项

这些比大型框架更容易产生实际价值，但不列为本次阶段收口前置条件。

| 小项 | 需求原因与实际内容 | 暂缓原因与启动条件 |
| --- | --- | --- |
| 运行工具可用性预检补充 | 针对 Godot/.NET/Codex 等实际 route 依赖，报告工具版本和不可用原因。复用现有身份、ACL、路径与 lease 检查。 | 现有 route 的执行诊断已能暴露故障；发生工具升级/部署迁移后再补该依赖的 probe，不建泛化环境管理器。 |
| 资产替换前后追溯增强 | 既有替换/回滚基础上，记录 before/after hash、引用范围、run 和结果，支持定位替换影响。 | 没有频繁替换或追踪困难时暂缓；出现真实定位问题后补记录，不重建资产系统。 |
| Type-kit 轻量一致性检查 | 在现有原生 C# 与说明之间检查首目标、能力与 marker，避免说明漂移。 | 当前数量有限，可随新增类型或改动进行；不以此强制迁移 JSON。 |

## 实施顺序与阶段收口

优先顺序为：普通项目生产 Runner 注册与 Windows 验证 → 当前业务链路验收及阻断原因读回 → 用实际新项目完成宿主部署/业务证据验证 → 按真实故障补上表小项 → 由 D1–D8 的具体触发条件决定扩展。

“当前规模下底层基本足够，完成接入与部署验证后可以阶段收口”不包含 D1–D8 全部实施。这些属于后置扩展；但不允许把缺失的最小业务机器证据、未验证的生产宿主或实际失败，归入暂缓来声称已经收口。

本次业务验收读取平台现有证据，不运行真实模型，也不自动生成尚缺失的规范 UI/validation sidecar。Windows/HTTP 夹具成功只证明实现与边界回归；实际项目只有在当前证据齐全且验收报告 passed 后才算完成。未执行生产验收时记录为“未验证”，不能由合并状态推断。
