一个重要纠正：HEAD 变化本身不需要 successor

你现在的理解是：

提交改变 HEAD，所以 Skill Input 必须重新刷新 successor。

但你的当前实现其实已经不是这样。

validate_skill_input_consumption.py 明确规定：

HEAD 只是 provenance；
验证时只比较 scoped index/worktree identity；
再逐个比较选中 source 的实际内容哈希；
无关提交不能使 frozen input 失效。

本次 prestart-39 的 29 个选中源码全部仍然匹配，因此：

这次并不是 HEAD 导致 successor 必须刷新，而是生成后 JSON 文件的表示字节发生了变化。

很可能是生成完成后，提交或格式化阶段重新排序了 JSON key、缩进或换行，导致 raw-byte SHA 失效。这正是你感觉“总在刷新”的真正来源。

当前最小修复

由于 prestart-39 已作为无效 generation 提交，按不可变 generation 原则，建议只做最后一次 prestart-40：

先运行所有 JSON formatter 和规范化工具。
再生成并 finalize prestart-40。
finalize 后禁止任何 formatter/pre-commit hook 改写 generation 文件。
--require-ready 验证通过。
更新 plan-validation、closure 和 implementation authorization。
重新生成唯一的 Quick Dev entry receipt。
将旧的 quick-dev-entry-validation.v1.json 标记为 historical/noncanonical。
提交后重新验证，但不要仅因 HEAD 改变再生成 prestart-41。

提交后如果选中源码不变，现有验证器理应继续接受 prestart-40。

高速演进阶段的哈希模型建议

我同意你的判断：当前体系对“表示字节”和“可变状态投影”绑定过严。严格性应该集中在语义授权边界，而不是所有 JSON 文件。

对象	建议身份	变化后的行为
authority scope、contract、command/test identity	强哈希，硬门禁	必须重新授权
selected path/role/resource-set	knowledgeSelectionHash / sourceSelectionHash	变化则阻断
选中源码内容	Merkle content root	同 selection 下自动 successor
JSON receipt/sidecar	JCS/RFC 8785 canonical JSON hash	key 顺序、缩进、换行不影响
plan-state、resume-state、current pointer	stateVersion + transitionEventId	不参与全局候选 raw hash
HEAD、报告、时间戳、诊断信息	provenance only	不触发 successor
publication、Acceptance、release	完整冻结和严格绑定	保持生产级强门禁

核心原则可以写成：

HEAD-only change
    -> continue
    -> no successor


JSON representation-only change
    -> canonical hash unchanged
    -> continue


same selection + selected source byte change
    -> automatic successor
    -> degraded execution allowed
    -> no maintainer reauthorization


contract / command / test / authority change
    -> hard block
    -> explicit reauthorization

最值得实施的三个改动是：

JSON 跨文件绑定使用 canonical semantic hash，不使用 raw-byte SHA。
授权回执只绑定一个 immutable generation root，不重复绑定 receipt、request、context、decision 四个原始文件。
HEAD 永久保持 provenance-only；不要让 successor 生成器看到新 HEAD 就自动刷新。

这样既不会降低真正的 authority 安全性，也能消除大部分无意义的 successor churn。

最终判定：NO-GO。需要修复 prestart-39 的内部字节绑定并重新发布一次入口证据；但不需要因为提交改变 HEAD 而无限生成 successor。
