绝大多数详细内容是 8-18 Quick Dev TDD 启动之前的准备与解阻步骤，并不是 8-18 本身的完整 Quick Dev 执行清单。

需要区分两个实施对象。

一、前置的工具链修复

W0–W6 属于独立的“工具链工作流修复计划”：

W0：类型化 source selection
W1：自动分页传输
W2：coverage/truncated 语义
W3：Knowledge 三门隔离
W4：不可变 generation 和 current pointer
W5：临时产物保留与清理
W6：端到端迁移测试

它们不是纯准备工作，其中包含真实代码修改，但应该由这个独立计划完成自己的：

VDD plan-ready
→ maintainer authorization
→ Quick Dev implementation
→ Acceptance

完成以后，8-18 才能可靠使用修复后的 Skill Input、Knowledge 和 receipt 编排能力。

二、8-18 的实施前修复

下面这些属于 8-18 Quick Dev 开始前必须完成的工作：

修复 canonical Skill Input contract
生成唯一的 current pointer
迁移或标记 skill-input-current2...current12
修复 authority manifest 分类
补全 finding set 和评审绑定
生成完整 baseline/candidate changed-set manifest
生成机器可验证的 root-cause/callsite inventory
修正 R3、R4 验收命令
修复 terminal 对失败 slice receipt 的错误接受
消除 repair closure 对 maintainer authorization 的循环依赖
生成并通过 plan-ready validator
将生命周期从 draft 推进到 plan-ready

这些完成后应停下来，等待 maintainer 发布：

implementation-authorized

因此，当前 a2ded39b 的 8-18 计划仍不能直接进入 Quick Dev。它还是计划修复阶段。

三、8-18 真正的 Quick Dev TDD 阶段

前面的方案只描述了这一阶段的原则，还没有展开成与前置阶段同等粒度的本地 Codex 操作手册。

8-18 的 Quick Dev 应当在授权后执行，建议按以下顺序。

Q0：启动前验证

Quick Dev 必须读取并验证：

plan-state.v1.json 状态为 implementation-authorized
maintainer authorization receipt 有效
implementation contract、registry、authority manifest 哈希一致
canonical Skill Input contract 和 current pointer 有效
Knowledge execution gate 允许执行
candidate identity 与授权对象一致
working tree 没有未分类变化
write set 没有超出授权范围

任何一项不满足，都不得开始写代码。

Q1：接管已存在的候选改动

由于在正式授权前已经出现了一些生产代码变化，Quick Dev 不能把它们伪造成新 RED。

应先生成：

pre-existing-candidate-delta.v1.json

记录：

baseline commit
candidate commit
每个已修改文件
before/after hash
所属 requirement/slice
pre-existing-behavior 或 pre-existing-candidate-change
采用 regression、补测试或回退的处置方式

然后将它们纳入受控候选，而不是重新制造 TDD 历史。

Q2：按 execution mode 执行各 slice

8-18 不应把所有 slice 都强制解释成经典 RED–GREEN–REFACTOR。

模式	用途	Quick Dev 行为
tdd	尚未实现的新行为	RED → GREEN → REFACTOR
regression	已存在或提前出现的行为	先证明基线/覆盖缺口，再增加回归测试
dogfood-replay	工作流自身验证	对真实计划执行只读/受限重放
default	尚未明确分类	应拒绝或要求补充 contract，不应自由解释

尤其是：

R3 应使用 regression
R4 应使用 dogfood-replay
只有确实尚未实现的新功能才能使用真正的 tdd
Q3：每个 TDD slice 的标准过程

对 execution_mode=tdd 的 slice：

检查授权 write set。
运行精确的 RED test node。
保存 RED receipt。
确认失败原因就是目标行为缺失。
实现最小生产代码。
运行精确 GREEN test node。
运行关联回归测试。
必要时重构。
再次运行精确测试与关联套件。
生成 slice receipt。

RED receipt 不能由以下失败冒充：

fixture 路径错误
import error
环境缺失
Knowledge publication failure
receipt 过期
与需求无关的已有测试失败
Q4：R3 regression 验证

R3 不做虚构 RED，而是：

通过 pytest --collect-only 固定精确 node ID。
验证 selector、test bytes、fingerprint。
验证 expected failure identity。
验证绑定的是指定的 8-17/8-18 candidate。
执行精确 node ID。
保存 command、exit code、stdout/stderr 摘要和输入哈希。
生成 status=pass 的 R3 receipt。

不能仅运行整个 test_plan_directory_loop.py 后就宣称 R3 完成。

Q5：R4 dogfood replay

R4 应使用计划本地只读验证器，例如：

tools/verify_8_17_read_only_dogfood.py

它需要证明：

执行前后 8-17 目录 manifest 完全一致
没有写入 8-17
只允许在 8-18 的声明范围内生成证据
所有 replay 都绑定同一 candidate
相同输入重复运行不会产生新的 action
不会无故创建 successor
receipt 和 current pointer 保持确定性
Q6：Quick Dev terminal

所有 slice 完成后运行 Quick Dev terminal。它必须拒绝以下情况：

slice receipt status != pass
failures 非空
receipt 绑定旧 candidate
receipt 绑定旧 Skill Input generation
receipt 缺少 contract/registry/authority hash
Knowledge execution gate 不允许执行
command timeout
R4 检测到 8-17 被修改
存在未授权写入

全部通过后才能生成：

implementation-complete

Quick Dev 不得直接生成 acceptance-passed。

Q7：独立 Acceptance

随后由 Acceptance Coordinator：

重新解析 current pointer
独立验证 candidate 和 changed set
执行注册验收命令
执行完整 Quick Dev 测试套件
执行完整 Acceptance 测试套件
验证 R3 regression evidence
验证 R4 dogfood replay
验证 Knowledge execution/publication/review 三门状态
验证没有越权写入
生成 acceptance receipt

通过后才进入：

acceptance-passed
准确结论

之前的方案是一个端到端修复路线，但工作量分布大约是：

工具链独立修复：完整实施工作
8-18 计划和证据修复：实施前工作
8-18 Quick Dev：只定义了边界和关键要求，尚未展开为逐文件、逐命令、逐 receipt 的完整执行脚本
Acceptance：定义了验收原则，但同样需要在最终 candidate 上实际执行

所以，本地 Codex现在不应该直接对 8-18 运行 Quick Dev TDD。正确顺序是：

工具链修复并验收
→ 修复 8-18 计划合同和证据
→ 8-18 达到 plan-ready
→ maintainer authorization
→ 运行 8-18 Quick Dev
→ implementation-complete
→ 独立 Acceptance

最关键的一点是：工具链修复的 Quick Dev 和 8-18 需求的 Quick Dev 是两次不同的受权实施，不能混在同一个候选提交和同一组 receipt 中。
