# PRD：BMAD 与 VDD 知识查询接入

## 0. 文档用途与当前结论

本 PRD 为仓库维护者和后续 SPEC、Architecture 阶段确定增量行为边界：让规划默认利用现有 Locator 定位知识，再核对原始来源与当前源码；查询不成为事实、实施完成或 Acceptance 权威。本轮只完成 PRD，不实施查询接线，也不启动后续阶段。

权威输入为 [原始需求 v1.0](sources/bmad-vdd-knowledge-query-requirements.md)，完整字节和来源元数据保存在 sources/。事实基线更新为 main 的 a1e783c569cb5a78ea8728c83518fd13c73a99e8；当前分支 feature/bmad-vdd-knowledge-query 尚无实施提交。详细核查路径和身份见 [addendum.md](addendum.md)。技能内部审核不等于逐阶段外部独立验收。

产品范围已足以形成 PRD；S2 执行排期仍须维护者确认（Q1）。本稿不据原文“不必等待”推导并行授权。用户已条件授权六阶段顺序交付：每阶段必须先获独立 Work 审核会话的 A/B 两组认可，且工作会话明确同意，才可进入下一阶段。当前暂停于 PRD 审核交接。

## 1. 愿景与问题

维护者在分析增量需求时，需要知道“仓库已经有什么、哪些只是计划、哪些约束仍有效”。已有知识索引能提供定位，但默认阶段触发和真实消费尚不完整；空结果也不能证明源码没有能力。若直接把历史计划当现状，后续实施可能重复建设或遗漏消费者。

本次复用现有 Locator 与配置能力，在 PRD、Architecture、SPEC 和 VDD 各自形成判断的时刻提供有界查询与来源核查。取舍是：规划可以在已确认的只读查询不可用时转为有记录的源码核查，但不能以可用性为由放过非法输入、损坏发布绑定或策略拒绝。development 的治理默认关闭保持不变。

## 2. 目标使用者与使用任务

目标使用者是维护 ji-mu-yun 工具链控制面的维护者及其 AI 助手。交互和 headless 都是需要覆盖的消费方式；本轮没有新增用户界面需求。

- 分析本仓增量需求时，先识别可复用能力、有效约束与明确排除项，再界定新增范围。
- 在 Architecture 做决定前核对 Accepted ADR、架构 owner 与实现；SPEC 保留已采纳来源，只补真正缺失的依据。
- 在 VDD create／实质性 repair 形成依赖切片之前核对调用方、测试和写入边界，避免重复实现。
- 恢复工作时识别相关来源变化，只更新受影响结论，保留历史身份。

这是单一维护角色的内部技术能力 PRD，采用能力分组，不虚构命名人物、业务旅程、市场目标或收益数字。Hosted 用户、游戏玩家和 Phase API 调用者不属于本轮用户面。

## 3. 术语与事实分类

- **Locator**：现有只返回定位、hash、来源和匹配信息的知识检索入口，不生成权威事实答案。
- **消费者身份**：受仓库策略约束的查询调用方；BMAD 身份需要正式声明，不能借用其他消费者。
- **来源身份**：区分已发布索引快照、当前 main、工作分支提交及未提交字节的定位与版本信息。
- **采纳结论**：读取有效来源后，对本次需求产生影响的判断及用途；不是完成证明。
- **治理**：既有强制校验、冻结、授权与证据流程；与本次轻量查询分别决定是否启用。
- **降级**：已识别的可用性或过期问题发生后，显式改用当前来源核查；不允许猜测必要事实。
- **fail-closed**：停止使用不可信结果并阻断受影响判断，直至按合同修正。
- **provenance**：仅承担溯源角色的输入；下游义务必须进入规范内容或适用 typed companion。
- **selection commitment**：现有外部来源选择绑定；其有效性不能代替正文完整性。
- **Acceptance**：既有正式验收 owner，查询与 PRD 内部审阅均不能代替它。

最新基线的分类结论如下：

| 分类 | 当前结论 |
| --- | --- |
| 已有且静态核实 | Locator、消费者策略/投影、VDD 治理分流、typed SPEC 外壳、官方配置覆盖点存在；不代表本次真实运行已验证 |
| 已有规划但未核实实现 | 历史目录和状态标记只作为线索，不据此声称已交付 |
| 拟新增 | BMAD 正式消费者、默认阶段查询、治理关闭时 VDD 查询及其真实消费验证 |
| 明确排除/延期 | Package B、S1/S2 游戏业务、沙箱重构及下文非目标 |
| 尚待核实 | 新接线实际行为、初次发布代次、Windows 路径/编码/子进程效果 |

PR #20 已拆分 jimuyun-spec／jimuyun-architecture 外壳，官方 BMAD 原生文件移出跟踪。当前仓库小型安装器只安装两外壳所需原生资源，不包含 PRD。Stock bmad-quick-dev 和旧 GDS/游戏设计兼容包已退役；quick-dev-tdd-adapter 仍保留。原始需求旧路径仅是历史证据，后续设计必须以最新 owner 为准。新定制必须外置，官方 BMAD 保持原样。

## 4. 能力与功能需求

保留原始 FR-01 至 FR-10 的稳定身份；下面是产品行为要求，不预定新 schema、具体预算数值或适配器实现。

### 4.1 配置与正式接入

#### FR-01：可维护且可核对的查询配置

维护者能够从仓库级配置确定查询入口、适用阶段、消费者身份、范围和有界预算，并检查解析后的有效值及来源。优先使用团队覆盖和现有解析器；升级覆盖的原生默认文件不能成为唯一持久配置。

遵守现有覆盖和数组合并语义；重复追加不能导致同一阶段同一触发重复执行。个人配置、模型输入和自然语言不能扩大仓库权限。必要配置缺失、配置非法和消费者不支持必须产生不同诊断，不得静默成功。

可观察结果：团队/个人覆盖后的有效值与来源可核对；重复触发被控制；缺失与非法输入的处理符合 FR-07。

#### FR-02：复用 Locator 并声明 BMAD 身份

BMAD 通过正式、受限的消费者身份查询；共享还是分阶段身份留给 Architecture。保持 Domain、Visibility、Lifecycle Instance、Enforcement Level 四维隔离及目录、策略、投影、发布绑定检查，不冒用 vdd 或 bootstrap。

所需消费者声明、策略生产来源及发布兼容增量纳入范围。不得手改生成投影、伪造发布记录或启用跳过发布/新鲜度检查的调试选项。初次需要有效新代次时，由维护者通过既有流程显式发布，日常查询不触发发布。

可观察结果：正式请求具备真实 BMAD 身份；权限和来源绑定未放宽；未发布或损坏绑定不能被空结果掩盖。

### 4.2 规划阶段实际消费

#### FR-03：PRD 默认查询

本仓需求 create 或实质性 update 在形成依赖仓库事实的范围判断前，执行针对性查询并读取影响判断的来源；不需要维护者额外提醒。输出区分已有且核实、仅有规划、明确排除/延期、拟新增及待核实。

纯排版/措辞且不改变事实判断时，可复用有效记录并写明理由。历史计划、勾选或报告不能独自证明实现完成。

可观察结果：查询和读取发生在结论前，实际改变复用/新增范围判断；纯编辑复用有可核对原因。

#### FR-04：Architecture 查询与 SPEC 承接

Architecture 在影响实现的决定前核对相关 Accepted ADR、owner、接口和当前实现，对照上游采纳结论，显式记录冲突与影响，不让索引摘要覆盖现行约束。

SPEC 保留有效能力、约束、排除项和未决问题；只为新问题、缺失依据或相关来源变化补查。继续使用 jimuyun-spec 所维护的 canonical SPEC 包、typed companion／provenance 和外部 selection commitment。只溯源的输入不能代替下游必须承担的规范内容。

可观察结果：来源冲突有处理；复用与补查理由可查；typed 角色、包完整性和 selection 规则保持有效。

#### FR-05：VDD 规划前查询与源码核对

VDD create／实质性 repair 在界定实现、消费者、测试和依赖切片前先查询，再读取当前源码、调用方、测试与控制契约。Locator 只缩小范围，不能替代调用链核查。

索引外文件可在授权范围内直接检索，记录为直接源码核查，不伪造成 Locator 返回。计划表达可复用能力、真实缺口及需要联动的消费者/测试；已存在行为应做回归验证，不能为制造 RED 走旧路径或重复实现。

可观察结果：未命中但源码已有能力时，计划采用既有能力并保留发现途径；写入边界和消费者检查有依据。

### 4.3 来源、失败与治理边界

#### FR-06：来源身份与采纳结论分开

影响判断的采纳信息保留查询主题、消费者、结果状态、来源定位、读取身份、简短结论及用途。相关但未采纳候选保留必要原因，不保存全部检索噪声。

索引快照、main、工作分支提交和未提交字节分别记录，不把旧发布快照改写为 HEAD，不把工作树新增能力声称为 main 已发布事实。已有 hash 验证合同继续执行，轻量查询不额外引入全仓冻结；正式计划和验收继续按原合同绑定。

可观察结果：读者可追溯每项影响范围的结论到底读了什么版本，能区分“已发布”和“候选”。

#### FR-07：可观察的失败与降级

消费者同时判断进程退出、超时/取消、输出可解析性、业务状态及来源完整性。退出码为 0、存在 JSON 输出或已生成文件，都不能单独证明查询成功。采用原始需求建议的以下产品语义；具体诊断/兼容映射由 SPEC 明确：

| 情况 | 普通规划查询或治理关闭 | 既有强制门禁 |
| --- | --- | --- |
| 命中且有效 | 读取后记录采纳/不采纳 | 继续原有门禁 |
| 未命中、低置信或歧义 | 定向核查源码，不能断言能力不存在 | required module 不满足则按合同阻断 |
| 已识别过期或相关来源变化 | 标记 degraded，核实当前来源，不消费失效候选 | 仅走现行 source_refresh/修复路径 |
| 确认入口不可用、未配置或超时 | 记录原因，改用独立源码核查；必要事实仍未知则停止依赖它的判断 | 不绕过 required gate |
| 非法请求/配置、未知或损坏状态、发布绑定损坏、越界或策略拒绝 | 停止消费并报错，修正后才继续受影响判断 | fail-closed |
| 用户取消 | 停止查询，保留未完成，不后台重试 | 保持取消/恢复边界 |

必要配置缺失可以被准确诊断后进入可用性处理；配置非法不得进入该降级通道。来源不能验证、约束冲突或事实缺口影响方案时应保留阻塞项。通用 blocked 无法判断原因时不能猜成未命中，需补最小只读诊断或适配。

可观察结果：退出码 0 的 blocked、损坏输出和越界不会被当成功或空结果；被拒绝内容不泄露。

#### FR-08：查询与治理解耦

保持现有治理优先级：显式选项覆盖环境配置，再按 phase state 解析；未设置 phase state 为 development，auto 在 development 关闭治理。默认查询不创建冻结知识、Skill-input attestation、额外授权、review lineage 或整套治理产物。

治理开启时继续强制校验、冻结和授权。若旧 ADR 与开发态轻量语义需要协调，由 Architecture 提出明确适用范围增量，不静默弱化正式模式。

可观察结果：development/auto 真实查询可发生而治理仍关闭；governance on 的 required module/完整性失败仍阻断。

### 4.4 恢复与交付证明

#### FR-09：局部刷新与有界上下文

任务意图和相关来源未变时可复用记录；进入新阶段或恢复时按实际依赖决定补查，不每轮加载全历史。相关变化只更新受影响结论和计划；无关代次/文件变化不单独触发整个需求重建、历史重写或全量重跑。正式计划有效性仍受原有范围绑定约束。

查询候选数、输出和调用次数必须有界，只装载支撑当前判断的片段。不得无限重试、自动发布或开启其他工作流修复查询。

可观察结果：相关变化产生局部更新；仅无关变化不触发重建；取消及预算耗尽不产生后台无限重试。

#### FR-10：真实消费验证与兼容交付

验证覆盖有效配置解析、阶段触发、真实查询/诊断、来源读取、结论被下游采用的完整链条。固定样例可验证确定性分支，但还需有界实际 BMAD 阶段与 VDD 消费样例；不得将伪造结果称为真实运行，不要求重跑历史全部需求。

保护 VDD compiler、Quick Dev TDD、SPEC 包完整性及 Acceptance 权威。针对实际改动路径回归，并单独验证 Windows 路径、编码、子进程行为；Linux 证据不能替代 Windows。

可观察结果：真实消费者记录能证明结论被采用，已有交接仍有效，未完成的平台验证明确标记。本 PRD 的内部检查不能满足未来功能实施 AC。

## 5. 跨能力质量要求

- **安全与权限**：配置覆盖和查询意图不能扩大仓库受控范围；损坏/越界结果不泄露内容，不绕过既有 gate。
- **可维护性**：官方 BMAD 文件保持字节原样，新定制外置；升级后仍可辨认有效配置来源，原生/外壳 owner 分清。
- **资源边界**：候选、输出、调用数设有限上界；具体数值由 SPEC 根据已有接口确定，不虚构延迟 SLA。
- **可审计性**：记录足以解释来源身份、失败、采纳和局部刷新；不建立第二套事实权威或全仓冻结。
- **兼容性**：保留正式治理与 typed SPEC/VDD/Quick Dev/Acceptance 合同；结果兼容策略先明确，再实施。

## 6. 范围、非目标与交付顺序

### 6.1 纳入范围

完整增量包含四类消费者的行为、最小身份/策略与结果适配、使用说明、必要 ADR/契约增量、针对性测试和可观察记录。不能只交配置文字就声称完成。

### 6.2 明确排除

- Package B 五个 Skill 的全面标准迁移；
- 重做 8-05、8-06、7-31；
- TC-D2/D4/D5/D6；
- Codex 内核、上下文压缩、自动新 thread、app-server/SDK；
- 新知识平台、向量库、通用 RAG、Memory/Miner、全仓索引重构或强制全量发布；
- Phase API/账号/生产节点/用户沙箱/Hosted 游戏功能；
- 自动 Bootstrap、总入口 Skill、内部 reviewer 平台或切片并行调度；
- 历史 plan/证据/代次改写；
- S1/S2 游戏业务和沙箱重构。

### 6.3 交付顺序与排期边界

产品阶段顺序保留为 PRD → SPEC → Architecture → 维护者显式请求 VDD → Quick Dev TDD → 正式 Acceptance 与逐阶段外部复核。当前执行在 PRD 阶段结束后暂停；后续授权以每阶段独立 A/B 审核和工作会话共同认可为条件。后续若实施 VDD 自身改造，使用稳定已验证工具链主持当前需求，候选只在隔离样例验证，并按现行 self-hosted 规则处理，不中途替换稳定工具链。

本需求在 Package A 后、Package B 前；验收合入 main 后新需求才能采用新查询能力。Package B 再做实际差异迁移，之后推进 7-31。游戏工作流重构正式 BMAD 规划建议采用本次合入后的能力，正式 VDD 建议等待 Package B 稳定，这些是版本安排。

**技术依赖不等于执行排期**：S2-06、S2-03A、S2-03B 可使用稳定工具链，表示本能力不是其新增技术运行依赖；是否现在开展、顺序如何由 Q1 决定，不授予并行执行权限。

## 7. 成功判据与验收场景

成功是来源核查真正影响复用/新增边界，失败分流可观察，默认治理不变，现有交接无已知实质回归，并由既有 Acceptance owner 完成正式验收。所有 14 个场景均为必须覆盖的行为；本次 PRD 不声称它们已执行通过。

不设未经输入支持的节省时长、命中率或延迟目标。反向约束是：不能追求更多命中而扩大权限，不能追求更高“完成率”而把 blocked 当缺失，不能追求记录数量而加载全部历史。查询次数或生成文件数量不作为成功指标。

| 编号 | 场景 | 必须观察到的结果 | 对应需求 |
| --- | --- | --- | --- |
| AC-01 | 在有团队覆盖的环境启动 PRD／Architecture | 有效配置正确；默认文件不被当作唯一持久配置；同一次触发无重复执行 | FR-01 |
| AC-02 | BMAD 通过正式查询路径请求知识 | 使用已声明 BMAD 身份及受限策略；未借用 VDD 身份；未放宽既有范围 | FR-02 |
| AC-03 | PRD 处理仓库已实现或已有规划的能力 | 查询后读取真实来源，准确区分已实现、仅计划和待核实；结论影响范围判断 | FR-03、FR-06 |
| AC-04 | Architecture 面对现有 ADR／实现约束 | 在决定前核对；冲突被显式处理，不能用历史摘要覆盖现行约束 | FR-04 |
| AC-05 | SPEC 承接及必要补查 | 规范内容与 provenance 正确分工；已有来源可复用，新事实缺口可补查；包校验保持有效 | FR-04 |
